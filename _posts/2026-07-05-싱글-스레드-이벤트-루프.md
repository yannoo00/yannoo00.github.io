uvicorn, node.j애쓰 처럼 싱글 스레드 이벤트 루프 기반 - 으로 대용량 요청을 빠르게 처리하는 기술이 있다.  

처음엔 서버가 싱글 스레드를 쓰면 너무 느린 것 아닌가 하는 생각이 들었다.  
물론 코어 수만큼 스레드를 띄워서 멀티 스레드 이벤트 루프를 돌리면 싱글 스레드보다 빠를 것이다.  
하지만 멀티 스레드는 단순히 성능으로만 접근하기에는 race condition 및 유지보수의 관점에서 여러 고난을 불러일으킬 수 있기 때문에 상황에 맞춰서 싱글 스레드 이벤트 루프를 선택할 수도 있고, javascript 탄생 시기에는 지금처럼 웹의 복잡도가 높지도 않았고 브라우저 안에서 가볍게 움직이는게 주 목표였기에 싱글 스레드로 고정되어 태어나게 되었다. 따라서 언어 자체에 lock 같은 멀티스레드 제어 기능이 없고, 언어의 런타임 자체를 이벤트 루프와 한 몸으로 만들어버린 것이다.  
여러 스레드를 돌려서 공유 자원에 접근할 때 - race condition, 데드락 등을 피하기 위해 작업하는 비용 + 그걸 위한 해결책으로 lock을 사용하는 등의 비용이 있는데, 싱글 스레드는 이런 문제로부터 자유롭다. 하지만 남아도는 코어를 어떻게 쓸 것이냐? -> 그냥 멀티 프로세스를 각 코어에 할당해서 띄우면 되는 것이다.  
각 프로세스는 싱글 스레드 기반이기 때문에 멀티 스레드 환경을 고려하지 않고 쉽게 코딩하되, 코어를 풀로 활용할 수 있다. 이 때 프로세스들이 서로 메모리를 공유해야 한다면 다른 중계 서버를 거치거나 redis 등을 활용할 수 있겠다.  

이벤트 루프는 크게 4가지 요소로 나뉘어 돌아간다.  
콜스택 -> Background(OS) -> Task Queue -> Event Loop -> (콜스택 -> ... )
- 콜스택: 메인 스레드가 실행중인 코드가 쌓이는 곳 (함수 호출 콜스택)
- Background: I/O, DB 쿼리 등 오래 걸리는 Non blocking 작업
- 태스크 큐: 백그라운드에서 처리되던 작업이 완료되면 OS가 해당 작업의 콜백을 이 큐에 밀어 넣는다.
- 이벤트 루프: 콜 스택이 비었는지 주기적으로 확인하면서, 비었다면 태스크 큐에서 하나를 꺼내어 콜스택으로 보내어 처리한다.  

즉 이벤트 루프는 CPU에서 돌아가는 작업으로 - 오래걸리는 작업이다. 여기서 cpu를 붙잡고 있는 어떤 작업을 시킨다면 싱글 스레드이기 때문에 멈추게 된다. 반드시 오랜 시간이 필요한 작업은 백그라운드에서 처리해야한다.  
네트워크, 데이터 I/O가 많은 웹서버에서는 관련 작업을 백그라운드에서 처리하고 cpu에서는 데이터 서빙, 간단한 사용자 상호작용을 담당하는 방식으로 효과적으로 사용이 가능하다.  
그럼 이 구조가 멀티스레드가 되면 어떻게 더 빨라지나? C# 멀티스레드 서버의 스레드 풀을 생각해보면, 이 태스크 큐(~=Job Queue)에서 일감을 꺼내가는 스레드가 싱글 스레드이냐, 여러 개의 worker 스레드 중 한 놈이냐가 다르다.  
그래서 생기는 문제 -  
```js
async function main() {
    console.log("1. 시작");
    const data = await fetch("https://api.com/data"); // 비동기 I/O
    console.log("2. 완료: ", data);
}
```


```C#
async Task MainAsync() {
    Console.WriteLine("1. 시작");
    var data = await httpClient.GetStringAsync("https://api.com/data"); // 비동기 I/O
    Console.WriteLine($"2. 완료: {data}");
}
```

js코드는 완료 로그가 찍히는 곳은 무조건 메인 스레드다. 왜냐면 싱글스레드니까.  
하지만 C# 코드에서 완료 로그가 찍히는 시점은 워커스레드 여러개중 하나가 된다. (물론 설정해서 호출자 스레드로 돌아오게  하는 것도 가능하다) 유니티 오브젝트들은 메인 스레드만 호출할 수 있기 때문에 다른 워커 스레드가 접근하다가 유니티 오브젝트를 건드리면 에러가 발생한다.
