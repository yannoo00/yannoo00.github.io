## 01. Compute

> SAA-C03에서 Compute는 "어떤 실행 환경을 고르고, 어떻게 비용/가용성/성능을 맞출까"를 묻는다.
> 핵심은 EC2 구매 옵션, Auto Scaling, 로드밸런서 3종 구분, Placement Group, 그리고 "운영 부담 최소화"라는 문구를 보면 관리형 서비스(Beanstalk, Batch, Lambda 등)로 기우는 감각이다.
> 수집된 문제에서 EC2는 S3 다음으로 가장 많이 언급되는 서비스다.

| 서비스 | 분류 | 한 줄 요약 | 시험 포인트 |
|---|---|---|---|

| EC2 Auto Scaling | 수평 확장 | 조건에 따라 인스턴스 수 자동 조절 | 정책 종류, 다중 AZ 배치, Launch Template, 헬스체크, Warm Pool |
| Elastic Load Balancing | 트래픽 분산 | ALB / NLB / GWLB / (CLB) | L7 vs L4, 고정 IP, 어플라이언스 삽입, Sticky session, Cross-zone |

| Instance Metadata (IMDS) | 메타데이터 | 169.254.169.254 | IMDSv2(토큰 기반) 강제, 자격증명 노출 방지 |
| Elastic Beanstalk | PaaS | 코드만 주면 EC2/ALB/ASG 자동 구성 | 운영 부담 최소 + 인프라 제어 일부 유지 |
| AWS Batch | 배치 | 작업 큐 기반 배치 컴퓨팅, Spot 활용 | 대량 배치 작업, 동적 프로비저닝 |
| Amazon Lightsail | 단순 VPS | 고정 요금 소규모 앱 | 거의 안 나옴, "가장 단순" 키워드 |
| AWS Outposts | 하이브리드 | AWS 하드웨어를 온프레미스에 | 데이터 로컬 처리 + AWS API 유지 |
| Local Zones / Wavelength | 엣지 컴퓨팅 | 대도시 근접 / 5G 네트워크 내 | 한 자릿수 ms 지연 요구 |
| EC2 Hibernate | 절전 | RAM을 EBS에 저장 후 중지 | 부팅 시간 단축, 세션 유지 |
| Enhanced Networking / EFA | 고성능 네트워크 | ENA, Elastic Fabric Adapter | HPC, MPI 워크로드 |
| AWS Compute Optimizer | 최적화 | 리소스 사용 분석 후 사이징 추천 | 과다 프로비저닝 비용 절감 |
| Elastic IP | 고정 공인 IP | 인스턴스에 붙이는 고정 IPv4 | 미사용 시 과금, NLB와 묶어 고정 IP 제공 |

### 핵심 개념 상세

#### EC2 인스턴스 패밀리
- **범용(T, M)**: 균형. T 계열은 버스트 크레딧 기반(Unlimited 모드 가능).
- **컴퓨팅 최적화(C)**: CPU 집약(배치, 미디어 트랜스코딩, 게임 서버).
- **메모리 최적화(R, X, z)**: 인메모리 DB, 대용량 캐시, SAP.
- **스토리지 최적화(I, D, H)**: 로컬 NVMe/HDD, 높은 순차/임의 I/O(NoSQL, 데이터 웨어하우스).
- **가속 컴퓨팅(P, G, Inf, Trn)**: GPU/ML 추론·학습.
- 시험 포인트: "메모리 집약" → R, "높은 로컬 디스크 IOPS" → I, "ML 추론 비용" → Inf.

#### EC2 구매 옵션
| 옵션 | 할인 | 조건 | 적합 워크로드 |
|---|---|---|---|
| On-Demand | 없음 | 즉시, 약정 없음 | 예측 불가, 단기 |
| Reserved (Standard) | 최대 ~72% | 1/3년, 인스턴스 속성 고정 | 안정적 상시 워크로드 |
| Reserved (Convertible) | 최대 ~66% | 1/3년, 패밀리 변경 가능 | 변화 가능성 있는 상시 |
| Savings Plans (Compute) | 최대 ~66% | 시간당 $ 약정, 패밀리/리전/OS 무관, Fargate·Lambda 포함 | 유연성 필요한 약정 |
| Savings Plans (EC2 Instance) | 최대 ~72% | 패밀리+리전 고정 | Standard RI 대체 |
| Spot | 최대 ~90% | 2분 전 통보 후 회수 | 중단 허용 배치, 빅데이터, CI, 무상태 ASG 일부 |
| Dedicated Host | 비쌈 | 물리 서버 전체 | BYOL 라이선스(소켓/코어 단위), 규제 |
| Dedicated Instance | 비쌈 | 물리 격리 but 호스트 제어 없음 | 격리만 필요 |
| Capacity Reservation | 할인 없음 | 특정 AZ 용량 예약 | 용량 확보 보장(RI/SP와 결합해 할인) |

- **Spot Fleet / EC2 Fleet**: 여러 풀에서 Spot+On-Demand 혼합 조달. `capacity-optimized` 전략이 중단 최소화.
- **Spot Block**은 폐지(2022). 시험에서는 "Spot은 언제든 회수"로 본다.
- 시험 포인트: "중단되면 안 되는 상시 워크로드 + 할인" → RI/Savings Plans, "중단 허용 + 최저 비용" → Spot, "라이선스가 물리 코어 단위" → Dedicated Host.

#### EBS-backed vs Instance Store
- **EBS**: 네트워크 블록 스토리지, 인스턴스 중지/재시작해도 유지, 스냅샷 가능. 단일 AZ.
- **Instance Store**: 호스트 로컬 디스크, 매우 높은 IOPS, **중지/종료 시 데이터 소멸**. 임시 캐시/버퍼/스크래치용.
- "인스턴스 중지 후에도 데이터 보존" → EBS. "최고 I/O, 데이터 소실 허용" → Instance Store.

#### Instance Metadata Service (IMDS)
- `http://169.254.169.254/latest/meta-data/`. IAM 역할 임시 자격증명도 여기서 조회됨.
- **IMDSv2**: 세션 토큰(PUT 후 GET) 필수, SSRF로 자격증명 탈취 방지. "메타데이터 보호 강화" → IMDSv2 강제(`HttpTokens=required`).
- User Data: 첫 부팅 시 1회 실행 스크립트(기본). 비밀을 넣지 말 것.

#### EC2 Auto Scaling
- 구성: **Launch Template**(권장, Launch Configuration은 레거시) + ASG(min/max/desired, 서브넷=AZ) + 스케일링 정책.
- 정책 종류
  - **Target Tracking**: "평균 CPU 50% 유지"처럼 목표값. 가장 쉬움, 시험 기본값.
  - **Step / Simple Scaling**: CloudWatch 알람 임계 구간별 증감.
  - **Scheduled**: 매일 9시 증설처럼 예측된 패턴.
  - **Predictive Scaling**: ML로 과거 패턴 학습해 사전 증설. "주기적 트래픽, 선제적으로" 키워드.
- **Cooldown**(기본 300초), **Warm-up**: 새 인스턴스가 메트릭에 반영되기 전 안정화 시간.
- **Lifecycle Hook**: 시작/종료 시 Pending:Wait / Terminating:Wait 상태로 커스텀 작업(로그 수거, 설정 다운로드).
- **Warm Pool**: 미리 초기화해둔 중지 인스턴스를 빠르게 투입(부팅 시간 긴 앱).
- **헬스체크**: EC2 상태 체크 기본, ELB 헬스체크 연동 권장(앱 레벨 장애도 교체).
- **종료 정책**: 기본은 "가장 많은 인스턴스가 있는 AZ → 가장 오래된 Launch Template → 다음 과금 시간에 가까운 것".
- **Instance Refresh**: 새 AMI로 롤링 교체.
- 다중 AZ에 걸쳐 ASG를 배치하면 AZ 장애 시 다른 AZ에 재분배된다. "고가용성" 문제의 기본 답.
- 스케일링 지표로 **ALB RequestCountPerTarget**을 쓰면 요청 수 기반 스케일링 가능.
- SQS 큐 길이(ApproximateNumberOfMessagesVisible)로 워커 ASG를 스케일링하는 패턴도 단골.

#### Elastic Load Balancing
| | ALB | NLB | GWLB |
|---|---|---|---|
| 계층 | L7 (HTTP/HTTPS/gRPC/WebSocket) | L4 (TCP/UDP/TLS) | L3 (IP, GENEVE 6081) |
| 라우팅 | 경로/호스트/헤더/쿼리/가중치 기반, 리다이렉트, 고정 응답 | 포트 기반 | 모든 트래픽을 어플라이언스로 |
| 고정 IP | ✗ (NLB 뒤에 두거나 Global Accelerator) | ✓ AZ당 Elastic IP | - |
| 성능 | 보통 | 초고성능, 초당 수백만 요청, 초저지연 | 어플라이언스 체인 |
| 대상 | 인스턴스, IP, Lambda, ECS 태스크 | 인스턴스, IP, ALB | 어플라이언스 인스턴스 |
| 클라이언트 IP 보존 | X-Forwarded-For 헤더 | 기본 보존(인스턴스 대상) / Proxy Protocol v2 | 보존 |
| TLS 종료 | ✓ | ✓ (TLS 리스너) | - |
| 대표 시나리오 | 마이크로서비스 경로 라우팅, WAF 연동 | 고정 IP 화이트리스트, UDP(VoIP/게임), 극한 성능 | 방화벽/IDS/IPS 서드파티 어플라이언스 투명 삽입 |

- **Cross-Zone Load Balancing**: ALB 기본 ON(무료), NLB 기본 OFF(활성화 시 AZ 간 데이터 전송 과금).
- **Sticky Session**: ALB 쿠키 기반(AWSALB / 앱 쿠키). 세션을 외부(ElastiCache/DynamoDB)로 빼는 게 더 좋은 설계.
- **Connection Draining(등록 취소 지연)**: 기본 300초, 진행 중 요청 완료 후 제거.
- **ALB + WAF**: ALB는 WAF 직접 연결 가능, NLB는 불가.
- **ALB 인증**: Cognito/OIDC로 리스너 레벨 인증 가능.
- **GWLB Endpoint**: 어플라이언스 VPC에 GWLB, 앱 VPC에 GWLB 엔드포인트를 두고 라우팅 테이블로 트래픽 유도.
- "헬스체크 실패한 인스턴스로 트래픽 안 보내기" → 모든 ELB 기본 기능.

#### Placement Groups
| 종류 | 배치 | 장점 | 단점 | 사용 |
|---|---|---|---|---|
| Cluster | 단일 AZ, 같은 랙 근접 | 최저 지연, 최고 네트워크 처리량(10Gbps+) | 랙 장애 시 전체 영향 | HPC, 빅데이터 노드 간 통신 |
| Spread | 서로 다른 랙(AZ당 최대 7개) | 랙 장애 격리 | 소규모(7/AZ) | 소수의 핵심 인스턴스 |
| Partition | 파티션(최대 7/AZ)별 랙 분리, 파티션당 다수 | 대규모 분산 시스템 장애 격리 | - | Hadoop, Cassandra, Kafka |

#### Elastic Beanstalk
- 코드 업로드 → EC2, ALB, ASG, RDS(선택), CloudWatch를 자동 구성. 인프라는 여전히 사용자 계정에 보이고 제어 가능.
- 배포 정책: All at once / Rolling / Rolling with additional batch / Immutable / Blue-Green(환경 URL 스왑).
- "개발자가 인프라 관리 없이 웹앱 배포, 하지만 EC2 제어는 유지" → Beanstalk. 완전 서버리스는 Lambda.

#### AWS Batch
- 작업 정의 + 작업 큐 + 컴퓨팅 환경(EC2/Spot/Fargate)으로 대량 배치. 의존성 있는 작업 체인 가능.
- "수천 개 배치 작업, 비용 최소, 스케줄링 자동화" → Batch (+Spot). 15분 이내 짧은 작업은 Lambda도 후보.

#### 하이브리드 / 엣지 컴퓨팅
- **Outposts**: 온프레미스에 AWS 랙. 데이터 주권/저지연 로컬 처리.
- **Local Zones**: 리전 외 대도시에 컴퓨팅/스토리지 확장. 한 자릿수 ms.
- **Wavelength**: 통신사 5G 엣지. 모바일 초저지연.
- **Snowball Edge Compute Optimized**: 네트워크 없는 환경에서 EC2/Lambda 실행.

#### 기타 자주 나오는 것
- **EC2 Hibernate**: RAM 내용을 루트 EBS에 저장. 재시작 시 메모리 상태 복원 → 부팅 긴 앱 빠른 재개. 루트 EBS 암호화 필수.
- **AMI 복사**: AMI는 리전 종속. 다른 리전에 배포하려면 복사. 암호화된 AMI 공유는 KMS 키 공유 필요.
- **EC2 Nitro**: 최신 하이퍼바이저 기반. EBS 성능 상한(io2 Block Express 등)은 Nitro 인스턴스 요구.
- **Burstable(T) 인스턴스**: 크레딧 소진 시 성능 저하. "간헐적 CPU 스파이크, 저비용" → T 계열 + Unlimited.
- **Elastic IP 제한**: 리전당 기본 5개. 고정 IP가 많이 필요하면 NLB 하나에 EIP를 두는 설계.

### 시험 단골 시나리오

- 중단 허용 배치/데이터 처리, 비용 최소 → **Spot Instances** (Spot Fleet, capacity-optimized).
- 1년 이상 안정적으로 돌아가는 서버, 인스턴스 타입 바꿀 수 있어야 함 → **Compute Savings Plans** (또는 Convertible RI).
- 기존 소프트웨어 라이선스가 물리 코어/소켓 단위 → **Dedicated Host**.
- 특정 AZ에 이벤트 기간 용량 확보 필수 → **On-Demand Capacity Reservation**.
- 트래픽 급증 시 자동 확장, 평균 CPU 60% 유지 → **ASG + Target Tracking**.
- 매주 월요일 9시 트래픽 급증이 예측됨 → **Scheduled Scaling** 또는 **Predictive Scaling**.
- 인스턴스 종료 전 로그를 S3로 복사해야 함 → **Lifecycle Hook (Terminating:Wait)**.
- 앱 부팅이 10분 걸려 스케일아웃이 느림 → **Warm Pool** 또는 미리 구운 AMI(Image Builder).
- 고정 IP로 방화벽 화이트리스트 필요 → **NLB + Elastic IP** (ALB는 고정 IP 없음).
- 경로(/api, /images)별로 다른 대상 그룹 → **ALB 경로 기반 라우팅**.
- UDP 기반 VoIP/게임 트래픽 분산 → **NLB** (ALB는 UDP 불가).
- 서드파티 방화벽 어플라이언스로 모든 트래픽 검사, 운영 부담 최소 → **Gateway Load Balancer**.
- 노드 간 초저지연 HPC → **Cluster Placement Group** (+ EFA, 같은 인스턴스 타입).
- 핵심 인스턴스 7대를 하드웨어 장애로부터 격리 → **Spread Placement Group**.
- Kafka/Hadoop 대규모 클러스터 장애 도메인 분리 → **Partition Placement Group**.
- SSRF로 인스턴스 자격증명 탈취 방지 → **IMDSv2 필수화**.
- 개발팀이 인프라 지식 없이 웹앱 배포, 운영 부담 최소 → **Elastic Beanstalk**.
- 온프레미스 데이터센터에서 AWS API로 저지연 처리, 데이터 로컬 보관 규제 → **Outposts**.
- 인스턴스 중지 후 메모리 상태 그대로 빠르게 복귀 → **Hibernate**.
- 다른 리전에 동일 서버 구성 복제 → **AMI 복사** 후 해당 리전에서 시작.
- 인스턴스 과다 프로비저닝 비용 줄이기 → **Compute Optimizer** 권장 사항 적용.

#### Reserved vs Savings Plans vs Spot
| | RI | Savings Plans | Spot |
|---|---|---|---|
| 약정 단위 | 인스턴스 속성 | 시간당 달러 | 없음 |

| | Cluster | Spread | Partition |
|---|---|---|---|
| 목표 | 성능(지연) | 소수 인스턴스 장애 격리 | 대규모 분산 시스템 장애 격리 |

| 규모 | 제한 없음(같은 타입 권장) | AZ당 7 | AZ당 파티션 7, 파티션당 다수 |

| 정책 | 트리거 | 예시 |
|---|---|---|
| Target Tracking | 목표 지표 유지 | CPU 50%, ALB 요청/대상 1000 |

| Simple | 알람 1개 → 1회 조정 후 쿨다운 | 레거시 |
| Scheduled | 시간 | 평일 08:00 desired 10 |
| Predictive | ML 예측 | 반복 패턴 선제 증설 |

## 02. Container

> 컨테이너 문제는 대부분 "ECS vs EKS", "EC2 런치 타입 vs Fargate", "이미지는 ECR", "태스크 권한은 IAM 역할"의 조합이다.
> "운영 부담 최소(least operational overhead)" + 컨테이너 → **Fargate**, "Kubernetes 호환/이식성" → **EKS**가 반사적으로 나와야 한다.
> 수집된 문제에서는 ECR, ECS, Fargate, EKS 순으로 언급된다.

### 핵심 개념 상세

#### Amazon ECS 구조
- **Cluster**: 태스크/서비스를 담는 논리적 그룹. 용량 공급자(Capacity Provider)로 EC2 ASG 또는 Fargate 연결.
- **Task Definition**: 컨테이너 이미지, CPU/메모리, 포트, 환경변수, 볼륨, IAM 역할, 네트워크 모드, 로그 설정을 담은 JSON 청사진(버전 관리됨).
- **Task**: Task Definition의 실행 인스턴스(컨테이너 1개 이상).
- **Service**: 원하는 수의 태스크를 유지하고 ALB/NLB와 연결, 롤링/블루그린 배포, 서비스 오토스케일링.
- **런치 타입**
  - **EC2**: 사용자가 EC2 인스턴스(ECS 에이전트 설치된 ECS 최적화 AMI)를 클러스터에 등록. 인스턴스 패치/스케일 책임 있음. GPU, 특정 인스턴스, 높은 밀도가 필요할 때.
  - **Fargate**: 인스턴스 없음. 태스크마다 vCPU/메모리 지정, AWS가 실행 환경 관리. "서버 관리 없음", "운영 부담 최소"의 정답.
- **Capacity Provider**: Fargate / FARGATE_SPOT / ASG 기반. 전략(base, weight)으로 비용 최적화(예: 기본 2개는 Fargate, 나머지는 Fargate Spot).

#### ECS IAM 역할 3가지 (단골)
| 역할 | 누가 사용 | 용도 |
|---|---|---|
| **Task Role** | 컨테이너 안의 앱 | 앱이 S3/DynamoDB 등 AWS API 호출 시 권한. 태스크마다 다르게 부여(최소 권한) |
| **Task Execution Role** | ECS 에이전트/Fargate | ECR 이미지 풀, CloudWatch Logs 전송, Secrets Manager/SSM에서 비밀 주입 |
| **Container Instance Role** (EC2 런치 타입) | EC2의 ECS 에이전트 | 클러스터 등록, 태스크 상태 보고 |

- "컨테이너 앱이 S3에 접근해야 한다" → **Task Role**에 S3 권한. 인스턴스 역할에 주면 모든 태스크가 공유하므로 오답.

#### ECS 네트워킹 모드
| 모드 | 설명 | 특징 |
|---|---|---|
| **awsvpc** | 태스크마다 ENI + 프라이빗 IP | Fargate 필수, 보안 그룹을 태스크 단위로 적용, 인스턴스당 ENI 수 제한 |
| bridge | Docker 기본 브리지 | 동적 포트 매핑 가능, EC2 런치 타입 |
| host | 호스트 네트워크 직접 사용 | 포트 충돌, 최고 성능 |
| none | 네트워크 없음 | 배치 작업 |

- **동적 포트 매핑 + ALB**: bridge 모드에서 호스트 포트를 0으로 두면 ALB가 임의 포트를 찾아 라우팅 → 한 인스턴스에 같은 컨테이너 여러 개.

#### ECS 스토리지
- **EFS**: 여러 태스크/AZ에서 공유되는 영구 스토리지. EC2·Fargate 모두 지원. "컨테이너 간 공유 파일 영구 저장" 정답.
- **EBS**: 태스크당 1개 볼륨 연결(2024~). 단일 태스크 고성능 블록.
- **Bind mount / Docker volume**: 호스트 디스크, 임시. Fargate는 태스크당 20GB(~200GB 확장) 임시 스토리지.
- **FSx for Windows**: Windows 컨테이너 공유 스토리지.

#### ECS 배포와 스케일링
- **Service Auto Scaling**: Application Auto Scaling으로 태스크 수 조절(Target Tracking: CPU/메모리/ALB 요청 수). EC2 런치 타입은 인스턴스 ASG도 함께 필요(Capacity Provider managed scaling이 자동화).
- **Rolling update**: minimumHealthyPercent / maximumPercent.
- **Blue/Green (CodeDeploy)**: 새 태스크 세트에 ALB 테스트 리스너로 검증 후 트래픽 전환. 빠른 롤백.
- **ECS Exec**: 실행 중 컨테이너에 셸 접속(SSM 기반), 디버깅.
- **Service Discovery**: Cloud Map에 `service.namespace` DNS 등록, 서비스 간 이름으로 호출. **ECS Service Connect**는 더 단순한 서비스 간 통신+메트릭.
- **비밀 주입**: Task Definition `secrets`에 Secrets Manager ARN 또는 SSM Parameter Store ARN → 환경변수로 주입(Task Execution Role 권한 필요). 이미지/환경변수에 평문 금지.
- **로그**: `awslogs` 드라이버 → CloudWatch Logs. FireLens(Fluent Bit)로 S3/OpenSearch/서드파티.

#### Amazon EKS
- 컨트롤 플레인(API 서버, etcd)은 AWS가 다중 AZ로 관리. 워커 노드는 선택:
  - **Managed Node Group**: AWS가 EC2 노드 프로비저닝/업그레이드. 일반적 정답.
  - **Self-managed Node**: 직접 관리.
  - **Fargate Profile**: 파드를 Fargate에서 실행(DaemonSet 불가, GPU 불가).
  - **EKS Auto Mode**(2024~): 노드/네트워크/스토리지까지 자동.
- **EKS Anywhere**: 온프레미스 쿠버네티스를 AWS가 지원. **EKS Distro**: AWS가 쓰는 쿠버네티스 배포판.
- 스토리지: **EBS CSI**(파드당 블록), **EFS CSI**(다수 파드 공유 ReadWriteMany), **FSx for Lustre CSI**(HPC).
- 네트워킹: **VPC CNI** → 파드가 VPC IP를 직접 받음. ALB는 **AWS Load Balancer Controller**(Ingress → ALB, Service LoadBalancer → NLB).
- 파드 권한: **IRSA**(IAM Roles for Service Accounts) 또는 **EKS Pod Identity**로 파드 단위 최소 권한.
- 오토스케일링: **Cluster Autoscaler** 또는 **Karpenter**(노드), HPA(파드).
- 쿠버네티스 기본 용어: Pod(컨테이너 묶음) → Deployment(복제/롤링) → Service(안정적 접근점) → Ingress(L7 라우팅).

#### Amazon ECR
- 프라이빗(계정 내, IAM 정책) / 퍼블릭(ECR Public Gallery).
- **Lifecycle Policy**: 태그 없는/오래된 이미지 자동 삭제로 비용 절감.
- **Image Scanning**: 기본 스캔(CVE), Enhanced 스캔(Inspector 연동, 지속 스캔).
- **Cross-Region / Cross-Account Replication**: 다중 리전 배포 시 이미지 자동 복제.
- **Pull Through Cache**: Docker Hub 등 퍼블릭 레지스트리 캐시.
- 이미지 암호화: 기본 AES-256(SSE-S3 방식), KMS 선택 가능. 불변 태그(Tag immutability)로 덮어쓰기 방지.
- 프라이빗 서브넷에서 ECR 풀: **VPC 엔드포인트**(ecr.api, ecr.dkr, 그리고 S3 게이트웨이 엔드포인트) 필요.

#### AWS App Runner
- 소스 리포지토리 또는 ECR 이미지를 주면 빌드→배포→HTTPS 엔드포인트→오토스케일까지 전부 관리.
- "웹 API 컨테이너를 가장 적은 인프라 지식으로 배포" → App Runner. VPC 커넥터로 RDS 접근 가능.

#### Fargate 세부
- 태스크당 vCPU 0.25~16, 메모리 0.5~120GB. Linux/ARM(Graviton)/Windows 지원.
- **Fargate Spot**: 최대 70% 할인, 2분 통보 후 중단. 중단 허용 배치/비핵심 서비스.
- Compute Savings Plans 적용 대상.
- 제약: 특권 컨테이너, GPU(EKS Fargate), DaemonSet 불가. 이런 요구가 있으면 EC2 런치 타입.

### 시험 단골 시나리오

- 컨테이너 실행, 서버/클러스터 관리 없이 운영 부담 최소 → **ECS on Fargate**.
- 온프레미스 Kubernetes 워크로드를 최소 변경으로 이전, 멀티클라우드 이식성 → **EKS**.
- 컨테이너 이미지를 안전하게 저장하고 취약점 스캔 → **ECR + Image Scanning**.
- 오래된 이미지 자동 정리로 스토리지 비용 절감 → **ECR Lifecycle Policy**.
- 여러 리전에 동일 컨테이너 배포 → **ECR Cross-Region Replication**.
- 컨테이너 앱이 DynamoDB에 접근 → **ECS Task Role**(인스턴스 역할 아님).
- DB 비밀번호를 컨테이너에 안전하게 전달 → **Secrets Manager + Task Definition secrets**(Execution Role 권한).
- 여러 컨테이너가 같은 파일을 읽고 쓰는 영구 공유 스토리지 → **EFS 볼륨**.
- 한 EC2에 같은 컨테이너 여러 개를 ALB로 분산 → **bridge 모드 + 동적 포트 매핑**.
- 태스크마다 별도 보안 그룹 적용 → **awsvpc 모드**.
- 비용 최적화된 배치 컨테이너, 중단 허용 → **Fargate Spot** (또는 ECS on EC2 Spot).
- GPU가 필요한 컨테이너 → **ECS/EKS EC2 런치 타입(GPU 인스턴스)**, Fargate 불가.
- 요청 수에 따라 컨테이너 수 자동 조절 → **ECS Service Auto Scaling (Target Tracking, ALBRequestCountPerTarget)**.
- 무중단 배포 + 즉시 롤백 → **ECS Blue/Green (CodeDeploy)**.
- 마이크로서비스 간 이름 기반 호출 → **ECS Service Discovery(Cloud Map)** 또는 **Service Connect**.
- 프라이빗 서브넷 Fargate 태스크가 인터넷 없이 ECR 이미지 풀 → **ECR 인터페이스 엔드포인트 + S3 게이트웨이 엔드포인트**.
- 소스코드만 있고 HTTPS 웹 서비스를 바로 띄우고 싶음 → **App Runner**.
- 온프레미스 서버에서 돌아가는 컨테이너를 AWS 콘솔로 관리 → **ECS Anywhere / EKS Anywhere**.
- EKS 파드별 최소 권한 AWS 접근 → **IRSA / Pod Identity**.

### 자주 헷갈리는 비교

#### 실행 환경 선택
| 요구 | 선택 |
|---|---|
| 컨테이너 + 최소 운영 + AWS 네이티브 | ECS Fargate |
| 컨테이너 + Kubernetes 호환/이식 | EKS (관리형 노드 or Fargate) |
| 웹 서비스 컨테이너 가장 단순 배포 | App Runner |
| 코드 배포, VM 제어 일부 필요 | Elastic Beanstalk |
| 이벤트 기반 단기(≤15분) 함수 | Lambda (컨테이너 이미지도 가능, 10GB) |
| 대량 배치 작업 큐 | AWS Batch (Fargate/EC2/Spot) |

#### EC2 런치 타입 vs Fargate
| | EC2 | Fargate |
|---|---|---|
| 인스턴스 관리 | 사용자 (AMI, 패치, ASG) | 없음 |
| 과금 | 인스턴스 시간 | 태스크 vCPU/메모리 초 단위 |
| GPU/특수 하드웨어 | 가능 | 불가(EKS Fargate 포함) |
| 밀도/비용 최적화 | 높은 밀도 가능, RI/Spot | Savings Plans, Fargate Spot |
| 네트워크 모드 | awsvpc/bridge/host | awsvpc만 |
| 적합 | 대규모 안정 워크로드, 특수 요구 | 변동 워크로드, 운영 최소 |

#### Task Role vs Task Execution Role vs Instance Role
| 질문 | 정답 |
|---|---|
| 앱 코드가 AWS 서비스 호출 | Task Role |
| ECR 풀, 로그 전송, 비밀 주입 | Task Execution Role |

## 03. Serverless & Application Integration

> 서버리스 문제의 핵심 단어는 "디커플링(decoupling)", "이벤트 기반", "운영 부담 최소", "급증 트래픽 완충"이다.
> Lambda의 한계값(15분, 10GB), SQS Standard vs FIFO, SNS fan-out, EventBridge 라우팅, Kinesis 스트리밍, API Gateway 캐싱/스로틀링을 숫자와 함께 외운다.
> 수집된 문제에서 Lambda는 전체 4위, SQS·API Gateway·SNS·Kinesis·EventBridge가 그 뒤를 잇는다.

### 핵심 개념 상세

#### AWS Lambda
- **한계값(외우기)**: 실행 시간 최대 **15분**, 메모리 128MB~**10GB**(CPU 비례), 임시 스토리지 /tmp 512MB~**10GB**, 배포 패키지 50MB(zip 직접)/250MB(압축 해제)/**컨테이너 이미지 10GB**, 동기 페이로드 6MB, 환경변수 4KB, 계정 동시 실행 기본 1,000(상향 가능).
- **동시성**
  - **Reserved Concurrency**: 함수에 동시성 상한/보장. 다른 함수가 다 쓰지 못하게 보호(또는 DB 연결 수 제한용 상한).
  - **Provisioned Concurrency**: 미리 초기화된 실행 환경 → 콜드 스타트 제거. 지연 민감 API.
  - **SnapStart**(Java 등): 초기화 스냅샷으로 콜드 스타트 단축.
- **호출 방식**: 동기(API Gateway, ALB, SDK), 비동기(S3, SNS, EventBridge → 내부 큐, 2회 재시도, Destinations/DLQ), 폴링(SQS, Kinesis, DynamoDB Streams → Event Source Mapping, 배치 처리).
- **VPC 연결**: 기본은 VPC 밖(인터넷 가능, VPC 내부 리소스 접근 불가). RDS 등 접근하려면 VPC 서브넷/보안 그룹 지정 → ENI 생성. 이때 인터넷이 필요하면 **프라이빗 서브넷 + NAT Gateway**(퍼블릭 서브넷에 두어도 공인 IP 없어 인터넷 불가).
- **RDS 연결 폭주**: Lambda 동시성이 DB 연결을 고갈 → **RDS Proxy**로 연결 풀링.
- **Layers**: 공통 라이브러리 공유. **환경변수**: 설정, KMS 암호화 가능. **Lambda@Edge / CloudFront Functions**는 Network 노트 참고.
- **Function URL**: API Gateway 없이 HTTPS 엔드포인트(IAM 인증 or 없음).
- **EFS 마운트**: 대용량/공유 파일 접근 가능(VPC 필요).
- **비용**: 요청 수 + GB-초. 메모리를 올리면 CPU도 올라 실행 시간이 줄어 총비용이 줄 수 있다.
- **멱등성**: 재시도가 있으므로 함수는 멱등하게. DynamoDB 조건부 쓰기 등.
- 시험 포인트: "15분 넘는 작업" → Lambda 불가 → Fargate/Batch/Step Functions 분할. "콜드 스타트 지연 없애기" → Provisioned Concurrency.

#### Amazon API Gateway
| | REST API | HTTP API | WebSocket API |
|---|---|---|---|
| 특징 | 풀 기능(캐싱, 사용량 계획, API 키, 요청 검증, WAF, 프라이빗) | 저비용(~70% 저렴), 저지연, JWT/OIDC 인증 내장 | 양방향 실시간(채팅, 알림) |
| 캐싱 | ✓ (0.5~237GB, TTL 기본 300초) | ✗ | - |
| 엔드포인트 | Edge/Regional/Private | Regional | Regional |

- **엔드포인트 타입**: **Edge-optimized**(CloudFront 경유, 글로벌 클라이언트), **Regional**(같은 리전, 직접 CloudFront 제어 가능), **Private**(VPC 엔드포인트로만 접근).
- **스로틀링**: 계정 기본 10,000 RPS, 버스트 5,000. **Usage Plan + API Key**로 고객별 할당량. 초과 시 429.
- **인증**: **IAM**(SigV4, 내부/서비스 간), **Cognito User Pool Authorizer**(앱 사용자), **Lambda Authorizer**(커스텀 토큰/서드파티 IdP), Resource Policy(IP/VPC/계정 제한).
- **통합**: Lambda(프록시 통합), HTTP(EC2/ALB), AWS 서비스(SQS/Kinesis/DynamoDB에 직접 → Lambda 없이), Mock, **VPC Link**(프라이빗 NLB/ALB 리소스).
- **캐싱**은 백엔드 부하와 지연을 동시에 줄인다. "반복 조회 API 응답 개선" → 캐시 활성화.
- **Stage / Canary 배포**: 트래픽 일부만 새 버전.
- 시험 포인트: "REST API 비용 절감, 간단한 Lambda 프록시" → HTTP API. "서드파티 개발자에게 API 키/쿼터" → REST API + Usage Plan.

#### Amazon SQS
- **Standard**: 무제한 처리량, **최소 1회 전달**(중복 가능), **최선 순서**(순서 보장 X).
- **FIFO**: **정확히 1회**(5분 중복 제거: Deduplication ID/콘텐츠 해시), **순서 보장**(Message Group ID 단위), 초당 300 msg(배치 3,000), High throughput 모드로 더 높게. 큐 이름 `.fifo`.
- **핵심 파라미터**: 메시지 크기 최대 **256KB**(더 크면 **SQS Extended Client Library**로 S3 참조), 보존 기본 **4일**, 최대 **14일**. **Visibility Timeout** 기본 30초(최대 12시간): 소비자가 처리 중인 메시지를 숨김. 처리 시간이 길면 늘리거나 `ChangeMessageVisibility`. **Long Polling**(WaitTimeSeconds 1~20초): 빈 응답 줄여 비용/지연 개선. **Delay Queue**(최대 15분), **Message Timer**.
- **DLQ(Dead-Letter Queue)**: maxReceiveCount 초과 메시지 격리 → 디버깅/재처리(Redrive).
- **Temporary Queue / Request-Response**: 요청-응답 패턴.
- **암호화**: SSE-SQS/SSE-KMS, 전송 중 TLS. **액세스 정책**: 크로스 계정, SNS 구독 허용.
- **소비자 스케일링**: ASG를 `ApproximateNumberOfMessagesVisible` 기반 Target Tracking(인스턴스당 백로그).
- 시험 포인트: "순서 보장 + 중복 없음" → FIFO. "메시지 처리에 10분, 중복 처리됨" → Visibility Timeout 증가. "실패 메시지 분석" → DLQ. "폴링 비용 줄이기" → Long Polling.

#### Amazon SNS
- 토픽에 발행 → 다수 구독자에 **푸시**: SQS, Lambda, HTTP/S, 이메일, SMS, 모바일 푸시, Kinesis Data Firehose.
- **Fan-out**: SNS → 여러 SQS 큐 → 각 큐를 다른 서비스가 독립 처리. 서비스 간 결합도 ↓, S3 이벤트 알림은 한 이벤트당 하나의 대상만 가능하므로 SNS fan-out 사용.
- **Filter Policy**: 구독자별 메시지 속성 필터(예: 주문 유형별 큐).
- **FIFO 토픽**: FIFO SQS 구독만 가능, 순서+중복 제거.
- **Message Data Protection**, 서버 측 암호화(KMS), 액세스 정책.
- SNS는 메시지를 **저장하지 않는다**(재시도 후 소실). 내구성 필요하면 SQS를 뒤에.
- 시험 포인트: "하나의 이벤트를 여러 시스템에 동시에" → SNS fan-out(+SQS). "일부 구독자만 특정 메시지" → Filter Policy.

#### Amazon EventBridge
- **이벤트 버스**: default(AWS 서비스 이벤트), partner(SaaS: Zendesk, Datadog 등), custom.
- **규칙(Rule)**: 이벤트 패턴 매칭 또는 **스케줄**(cron/rate; 신규 기능은 **EventBridge Scheduler**: 일회성/반복, 타임존, 1,300만 스케줄). 대상: Lambda, SQS, SNS, Step Functions, Kinesis, ECS 태스크, API Destination(외부 HTTP), 다른 계정/리전 버스.
- **아카이브 & 재생(Replay)**: 이벤트 저장 후 재처리. **스키마 레지스트리**: 이벤트 구조 자동 발견, 코드 바인딩.
- **Pipes**: 소스(SQS/Kinesis/DynamoDB Streams)→필터→강화→대상 포인트 투 포인트.
- CloudWatch Events의 후속. "AWS 리소스 상태 변경(예: EC2 상태, GuardDuty 발견) 시 자동 대응" → EventBridge 규칙 → Lambda/SNS.
- vs SNS: EventBridge는 콘텐츠 기반 필터링·스키마·SaaS 통합·아카이브가 강점. 대규모 팬아웃/모바일 푸시/SMS는 SNS.

#### AWS Step Functions
- JSON(ASL) 상태 머신: Task(Lambda/서비스 호출 200+), Choice, Parallel, Map(대량 병렬), Wait, Pass, Succeed/Fail. 재시도(Retry)/오류 처리(Catch) 내장.
- **Standard**: 최대 1년, 정확히 1회, 실행 이력 보존, 사람 승인 대기(콜백 토큰 `.waitForTaskToken`).
- **Express**: 최대 5분, 최소 1회(비동기)/최대 1회(동기), 고빈도(초당 10만+), 저비용. IoT 수집, 스트리밍 변환.
- 시험 포인트: "여러 Lambda를 순서/분기/병렬로 조율, 실패 재시도, 시각화" → Step Functions. "수동 승인 단계" → Standard + 콜백.

#### Amazon Kinesis
- **Data Streams**: 샤드당 쓰기 **1MB/s 또는 1,000 레코드/s**, 읽기 **2MB/s**(모든 소비자 공유) → **Enhanced Fan-Out**으로 소비자당 2MB/s 푸시. 레코드 최대 1MB. 보존 **24시간 기본, 최대 365일**. 파티션 키로 샤드 결정("hot shard" 주의). **On-demand 모드**는 샤드 관리 없음. 소비자: Lambda, KCL 앱, Firehose, Flink. 데이터 **재처리(replay) 가능**.
- **Data Firehose**: 완전 관리형 적재. 소스(Direct PUT, Data Streams, MSK) → 변환(Lambda, 포맷 변환 Parquet/ORC) → 대상(**S3, Redshift, OpenSearch, Splunk/Datadog/HTTP**). **버퍼링**(1~128MB 또는 0~900초)으로 **거의 실시간(near real-time)**, 재생 불가, 샤드 없음, 자동 스케일. "스트리밍 데이터를 S3에 Parquet로 저장, 관리 최소" 정답.
- **Managed Service for Apache Flink**: 스트림에 SQL/Flink 쿼리(윈도우 집계, 이상 탐지).
- **Video Streams**: 카메라 영상 스트리밍 → ML 분석.
- 시험 포인트: "실시간(밀리초~초), 여러 소비자, 재처리" → Data Streams. "S3/Redshift에 적재, 코드 없이" → Firehose. "스트림 실시간 집계 SQL" → Flink. "Kafka 호환 필수" → MSK.

#### Amazon MQ
- ActiveMQ/RabbitMQ 관리형. 온프레미스 앱이 **JMS, AMQP, MQTT, OpenWire, STOMP** 같은 표준 프로토콜을 쓰고 코드 변경 없이 이전할 때. 다중 AZ(active/standby), EFS 저장. 신규 클라우드 네이티브는 SQS/SNS.

#### Amazon Cognito
- **User Pool**: 사용자 디렉터리·로그인(이메일/소셜/SAML/OIDC), JWT 발급, MFA, 호스팅 UI. API Gateway/ALB 인증 연동.
- **Identity Pool(Federated Identities)**: User Pool/소셜/SAML 사용자 또는 **게스트**에게 **STS 임시 AWS 자격증명** 발급 → S3/DynamoDB 직접 접근(IAM 역할 매핑).
- 시험 포인트: "모바일 앱 사용자 로그인/가입" → User Pool. "로그인한 사용자가 자기 S3 폴더에 직접 업로드" → Identity Pool + IAM 역할.

#### 디커플링 패턴
- **Queue-based load leveling**: 프런트(API/EC2) → SQS → 워커(Lambda/ASG). 급증 트래픽을 큐가 흡수, 백엔드(DB)는 일정 속도로 처리. 메시지 유실 없음.
- **Fan-out**: SNS → 다수 SQS/Lambda. 하나의 이벤트를 독립 소비자가 병렬 처리.
- **Event-driven**: S3/DynamoDB Streams/EventBridge → Lambda. 폴링 없이 반응.
- **Orchestration(Step Functions) vs Choreography(이벤트 버스)**: 중앙 제어 vs 각 서비스가 이벤트에 반응.
- **Idempotency + DLQ + 재시도**: 서버리스 신뢰성 3종 세트.

### 시험 단골 시나리오

- 메시지 순서 보장 + 정확히 한 번 처리 → **SQS FIFO**.
- 주문 급증 시 DB 과부하 방지, 메시지 유실 금지 → **SQS Standard + 워커 ASG/Lambda**(queue-based load leveling).
- 하나의 업로드 이벤트를 썸네일·메타데이터·알림 3개 시스템이 각각 처리 → **S3 → SNS → 3개 SQS → 각 Lambda**.
- 소비자가 메시지를 2번 처리함 → **Visibility Timeout 늘리기**(또는 FIFO/멱등 처리).
- 처리 실패 메시지를 따로 모아 분석 → **DLQ**.
- SQS 빈 응답 과다 비용 → **Long Polling**.
- 1MB 이미지 메타를 큐로 전달 → **S3 저장 + SQS Extended Client(참조만 전달)**.
- 온프레미스 ActiveMQ/JMS 앱을 코드 변경 없이 이전 → **Amazon MQ**.
- Lambda가 Aurora 연결을 고갈시킴 → **RDS Proxy**.
- Lambda가 프라이빗 RDS 접근 + 외부 API도 호출 → **VPC 프라이빗 서브넷 + NAT Gateway**.
- API 콜드 스타트 지연 제거 → **Provisioned Concurrency**.
- 특정 Lambda가 전체 동시성을 소진해 다른 함수 영향 → **Reserved Concurrency**.
- 20분 걸리는 처리 → Lambda 불가 → **Fargate / Batch / Step Functions로 분할**.
- 반복 조회 API 백엔드 부하·지연 감소 → **API Gateway 캐싱**.
- 파트너별 API 호출량 제한·키 발급 → **API Gateway Usage Plan + API Key**.
- 모바일 사용자 인증 후 API 호출 → **Cognito User Pool + API Gateway Cognito Authorizer**.
- 사내 VPC에서만 접근 가능한 API → **Private API + VPC 엔드포인트**.
- 여러 Lambda를 순서/분기/재시도로 조율, 사람 승인 포함 → **Step Functions Standard**.
- IoT 센서 초당 수만 건 수집, 여러 앱이 실시간 소비, 7일 재처리 → **Kinesis Data Streams(보존 7일, Enhanced Fan-Out)**.
- 클릭스트림을 S3에 Parquet로 거의 실시간 적재, 코드 최소 → **Firehose(+Lambda 변환/포맷 변환)**.
- 스트림에서 5분 윈도우 이상 탐지 → **Managed Service for Apache Flink**.
- EC2 상태 변경/GuardDuty 발견 시 자동 Lambda 대응 → **EventBridge 규칙**.
- SaaS(Zendesk 등) 이벤트를 AWS로 → **EventBridge Partner Event Source**.
- 매일 새벽 2시 Lambda 실행 → **EventBridge Scheduler(cron)**.
- 이벤트 유실 시 재처리 필요 → **EventBridge Archive & Replay**.
- 기존 이메일 발송량 많음(트랜잭션 메일) → **SES**(SNS 이메일은 알림용).

## 04. Storage

> SAA-C03에서 가장 많이 나오는 영역. 수집된 문제에서 **S3가 1위**(EC2보다 많음), EBS 6위, Backup·Glacier·FSx·EFS·Storage Gateway·DataSync·Snowball이 뒤를 잇는다.
> 패턴은 세 가지: (1) 어떤 S3 클래스/수명주기가 가장 싼가, (2) 블록(EBS) vs 파일(EFS/FSx) vs 객체(S3) 중 무엇인가, (3) 온프레미스 ↔ AWS 데이터 이동 도구(Storage Gateway/DataSync/Snow/Transfer Family) 중 무엇인가.

### 핵심 개념 상세

#### Amazon S3 기본
- 버킷은 **리전**에 속하며 이름은 전역 고유. 객체 최대 **5TB**, 단일 PUT 5GB → **Multipart Upload**(100MB 이상 권장, 5GB 이상 필수).
- **Strong read-after-write consistency**(2020~): PUT 후 즉시 최신 읽기.
- 내구성 99.999999999%(11 9's), 가용성은 클래스별.
- **성능**: 접두사(prefix)당 초당 **3,500 PUT/COPY/POST/DELETE, 5,500 GET**. 접두사를 나누면 선형 확장. **Byte-Range Fetch**로 병렬 다운로드/부분 조회.
- **S3 Select / Glacier Select**: SQL로 객체 내부 일부만 가져와 전송량·비용 절감(CSV/JSON/Parquet).
- **Event Notification**: 객체 생성/삭제/복원 이벤트 → SNS / SQS / Lambda / EventBridge(모든 이벤트, 고급 필터).

#### S3 스토리지 클래스
| 클래스 | 가용성 | AZ | 최소 보관 | 검색 비용/시간 | 용도 |
|---|---|---|---|---|---|
| Standard | 99.99% | ≥3 | 없음 | 없음 / 즉시 | 자주 접근, 기본 |
| Intelligent-Tiering | 99.9% | ≥3 | 없음(모니터링 비용 소액) | 없음 / 즉시(아카이브 티어 선택 시 분~시간) | **접근 패턴 불명/변동** |
| Standard-IA | 99.9% | ≥3 | 30일 | GB당 검색 비용 / 즉시 | 드물게 접근, 빠른 복구(백업, DR) |
| One Zone-IA | 99.5% | 1 | 30일 | GB당 / 즉시 | 재생성 가능한 2차 복사본, AZ 손실 허용 |
| Glacier Instant Retrieval | 99.9% | ≥3 | 90일 | GB당 / **밀리초** | 분기 1회 접근 아카이브(의료 영상, 뉴스) |
| Glacier Flexible Retrieval | 99.99%(복원 후) | ≥3 | 90일 | Expedited 1~5분 / Standard 3~5시간 / Bulk 5~12시간(무료) | 연 1~2회 접근 백업 |
| Glacier Deep Archive | 99.99%(복원 후) | ≥3 | 180일 | Standard 12시간 / Bulk 48시간 | 규제 보관 7~10년, 최저 비용 |
| Express One Zone | 99.95% | 1 | 없음 | 한 자릿수 ms | 초고성능 ML/분석 임시 데이터 |

- 수명주기 전환은 **아래 방향으로만**(Standard → IA → Glacier…). 최소 보관 기간 전 삭제/전환 시 남은 기간 과금. 128KB 미만 객체는 IA 전환 비효율(과금 최소 단위).
- "접근 패턴을 모른다 / 예측 불가" → **Intelligent-Tiering**. "AZ 손실에 견뎌야 함" → One Zone-IA 제외.

#### S3 Lifecycle
- **Transition**: N일 후 다른 클래스로. **Expiration**: N일 후 삭제(이전 버전, 불완전 멀티파트 업로드 정리도 가능).
- 흐름 예: `Standard --30일--> Standard-IA --90일--> Glacier Flexible --365일--> Deep Archive --7년--> 만료`
- 필터: 접두사, 태그, 객체 크기. **S3 Storage Class Analysis**로 전환 시점 분석.
- "불완전 멀티파트 업로드가 비용 발생" → 수명주기 규칙으로 7일 후 중단/삭제.

#### S3 버저닝 · 삭제 보호
- **Versioning**: 버킷 단위. 덮어쓰기/삭제 시 이전 버전 보존(삭제는 Delete Marker). 비활성화 불가(일시 중단만).
- **MFA Delete**: 버전 영구 삭제/버저닝 중단에 MFA 요구(루트만 설정, CLI).
- **Object Lock (WORM)**: 버저닝 필수.
  - **Governance 모드**: 특수 권한(`s3:BypassGovernanceRetention`) 있으면 삭제 가능.
  - **Compliance 모드**: **루트 포함 누구도** 보존 기간 내 삭제/변경 불가. 규제(SEC 17a-4, FINRA).
  - **Legal Hold**: 기간 없이 보존, 권한 있으면 해제.
- **Glacier Vault Lock**: Glacier 볼트 정책을 잠가 변경 불가(레거시 Glacier API).

#### S3 복제
- **CRR(Cross-Region)**: 다른 리전으로 비동기 복제. 지연 감소, DR, 규정 준수. **SRR(Same-Region)**: 로그 집계, 프로덕션→테스트 복제.
- 요구: **양쪽 버저닝 활성화**, IAM 역할. 기본은 **새 객체만**(기존 객체는 **S3 Batch Replication**). 삭제 마커 복제는 옵션, 버전 삭제는 복제 안 됨. 체이닝 안 됨.
- **RTC(Replication Time Control)**: 15분 내 99.99% 복제 SLA.
- **Multi-Region Access Point**: 여러 리전 버킷을 하나의 글로벌 엔드포인트로, 가장 가까운 리전 라우팅, 장애 조치.

#### S3 암호화
| 방식 | 키 관리 | 특징 |
|---|---|---|
| **SSE-S3** | AWS(AES-256) | 기본값(2023~ 모든 신규 객체), 헤더 `x-amz-server-side-encryption: AES256` |
| **SSE-KMS** | KMS 키(AWS 관리 or 고객 관리) | 키 사용 감사(CloudTrail), 키 정책으로 접근 통제, KMS API 호출 한도 → **S3 Bucket Key**로 요청 99% 감소 |
| **DSSE-KMS** | KMS, 이중 암호화 | 규제상 2중 암호화 요구 |
| **SSE-C** | 고객이 키를 매 요청에 제공 | AWS는 키 저장 안 함, HTTPS 필수 |
| **Client-side** | 고객이 업로드 전 암호화 | AWS는 평문 절대 못 봄 |

- 전송 중 암호화 강제: 버킷 정책 `aws:SecureTransport: false` → Deny.
- "키 사용 추적/감사가 필요" → SSE-KMS. "AWS가 키를 절대 보유하면 안 됨" → SSE-C 또는 클라이언트 측.

#### S3 접근 제어
- **IAM 정책**(사용자 기준) + **버킷 정책**(리소스 기준, 크로스 계정/퍼블릭/조건) + **ACL**(레거시, 기본 비활성화 권장) + **Block Public Access**(계정/버킷 단위 안전장치).
- **Presigned URL**: 임시(기본 1시간, 최대 7일) 업로드/다운로드 링크. "로그인 사용자에게만 잠시 다운로드 허용".
- **S3 Access Points**: 앱/팀별 전용 엔드포인트+정책. 대규모 공유 버킷 정책 단순화. VPC 전용 액세스 포인트 가능.
- **S3 Object Lambda**: GET 시 Lambda로 데이터 변환(마스킹, 리사이즈)해 반환, 원본 복사본 불필요.
- **VPC Gateway Endpoint**: 프라이빗 서브넷에서 인터넷/NAT 없이 S3 접근, 무료. 버킷 정책 `aws:sourceVpce` 조건으로 제한.
- **Requester Pays**: 데이터 전송/요청 비용을 다운로드하는 쪽이 부담(대용량 공개 데이터셋).
- **CORS**: 다른 도메인의 브라우저 스크립트가 버킷 접근 시 필요.
- **정적 웹 호스팅**: 버킷 웹사이트 엔드포인트(HTTP). HTTPS/커스텀 도메인은 **CloudFront + OAC**로.

#### S3 기타 운영 기능
- **S3 Storage Lens**: 조직 전체 스토리지 사용·활동 대시보드. **S3 Inventory**: 객체 목록 보고서(CSV/Parquet).
- **S3 Batch Operations**: 수십억 객체에 태그/복사/ACL/복원/Lambda 일괄 실행.
- **S3 Transfer Acceleration**: 엣지 로케이션으로 업로드 → AWS 백본으로 버킷. 장거리·대용량 업로드 가속, GB당 추가 요금.
- **Server Access Logging / CloudTrail 데이터 이벤트**: 요청 감사.
- **S3 Glacier 복원**: `RestoreObject`로 임시 복사본(기간 지정). 복원 완료 이벤트로 알림.

#### Amazon EBS
| 타입 | 종류 | IOPS | 처리량 | 크기 | 부트 | 용도 |
|---|---|---|---|---|---|---|
| **gp3** | SSD | 3,000 기본, 최대 16,000(크기 독립) | 125MB/s 기본, 최대 1,000 | 1GB~16TB | ✓ | 기본값, gp2보다 20% 저렴 |
| gp2 | SSD | 3 IOPS/GB(버스트 3,000), 최대 16,000 | 최대 250 | 1GB~16TB | ✓ | 레거시 |
| **io1 / io2** | SSD | 최대 64,000(io2 Block Express 256,000) | 최대 1,000(BE 4,000) | 4GB~16TB(BE 64TB) | ✓ | DB, 지연 민감, **Multi-Attach** |
| st1 | HDD | 최대 500 | 최대 500MB/s | 125GB~16TB | ✗ | 빅데이터, 로그, 순차 대용량 |
| sc1 | HDD | 최대 250 | 최대 250MB/s | 125GB~16TB | ✗ | 가장 저렴, 드문 접근 |

- **단일 AZ**. 다른 AZ로 옮기려면 **스냅샷 → 새 볼륨**. 다른 리전은 스냅샷 복사.
- **스냅샷**: S3에 증분 저장, 삭제해도 다른 스냅샷 복원 가능. **Fast Snapshot Restore(FSR)**: 복원 볼륨 즉시 최고 성능(초기화 지연 없음), AZ당 과금. **Snapshot Archive**: 75% 저렴, 복원 24~72시간. **Recycle Bin**: 실수 삭제 복구(보존 규칙). **Data Lifecycle Manager(DLM)**: 스냅샷 스케줄/보존 자동화.
- **암호화**: KMS. 암호화 볼륨의 스냅샷·복원 볼륨 모두 암호화. 암호화 안 된 볼륨 → 스냅샷 → **복사 시 암호화** → 새 볼륨. 계정 기본 암호화 설정 가능.
- **Multi-Attach**: io1/io2만, 같은 AZ 최대 16개 Nitro 인스턴스, **클러스터 인식 파일시스템** 필요(일반 ext4/XFS 불가).
- **Elastic Volumes**: 중단 없이 크기/타입/IOPS 변경(크기는 증가만).
- **EBS 최적화 인스턴스**: EBS 전용 대역폭. 루트 볼륨 `DeleteOnTermination` 기본 true(데이터 볼륨은 false).
- vs **Instance Store**: 물리 로컬, 최고 IOPS, 중지/종료 시 소멸, 스냅샷 불가.

#### Amazon EFS
- **NFSv4**, 리전 서비스, **여러 AZ의 수천 인스턴스 동시 마운트**, 자동 확장(페타바이트), 사용량 과금. **Linux 전용**(Windows 불가).
- 클래스: **Standard(Regional)** 다중 AZ / **One Zone** 단일 AZ(저렴). 각각 **IA**와 **Archive** 티어 → **수명주기 정책**(N일 미접근 시 IA로, 접근 시 복귀 옵션)으로 비용 최대 90% 절감. **Intelligent-Tiering** 자동화.
- **성능 모드**: General Purpose(기본, 저지연) / Max I/O(수백~수천 클라이언트 병렬, 지연 약간↑, Elastic 처리량과 비호환).
- **처리량 모드**: **Elastic**(기본 권장, 자동) / Bursting(크기 비례) / Provisioned(크기와 무관하게 고정 처리량).
- **Access Points**: 앱별 루트 디렉터리/POSIX 사용자 강제. IAM으로 마운트 권한 제어, 전송 중 TLS, 저장 시 KMS.
- **Replication**: 다른 리전/AZ로 복제(DR). **AWS Backup** 통합.
- Lambda, ECS/Fargate, EKS 모두 마운트 가능. 온프레미스에서 Direct Connect/VPN 통해 마운트 가능.
- 시험 포인트: "여러 EC2(다중 AZ)가 같은 파일 공유, Linux" → EFS. "Windows 공유" → FSx for Windows. "EFS 비용 절감" → IA 수명주기.

#### Amazon FSx
- **for Windows File Server**: SMB, NTFS, **Active Directory**(AWS Managed AD 또는 자체 AD) 통합, Windows ACL, DFS 네임스페이스, 단일/다중 AZ, SSD/HDD, 중복 제거, 섀도 복사본, 온프레미스 접근 가능. "Windows 앱 공유 드라이브, AD 권한 유지" 정답. Linux도 SMB 클라이언트로 마운트 가능.
- **for Lustre**: HPC/ML/비디오 처리용 병렬 파일시스템, 수백 GB/s, 밀리초 미만 지연. **S3와 연동**(S3를 지연 로딩, 결과 다시 S3로 내보내기). **Scratch**(임시, 복제 없음, 저렴) vs **Persistent**(복제, 장기). Linux 전용.
- **for NetApp ONTAP**: NFS·SMB·iSCSI **다중 프로토콜**, 스냅샷, 복제(SnapMirror), 중복 제거·압축, 씬 프로비저닝, 자동 티어링. 온프레미스 NetApp 사용 조직 이전, Linux+Windows 동시 접근.
- **for OpenZFS**: ZFS 기반 NFS, 스냅샷/클론 즉시, 수십만 IOPS, 저지연. Linux/Windows/macOS NFS 클라이언트.
- **FSx File Gateway**: 온프레미스에서 FSx for Windows 캐시 접근.

#### AWS Storage Gateway
| 타입 | 프로토콜 | 데이터 위치 | 용도 |
|---|---|---|---|
| **S3 File Gateway** | NFS/SMB | S3에 객체로 저장, 로컬 캐시 | 온프레미스 앱 파일을 S3로 확장/백업, S3 수명주기 적용 |
| **FSx File Gateway** | SMB | FSx for Windows | 온프레미스 Windows 공유를 FSx로 |
| **Volume Gateway – Cached** | iSCSI | **S3가 원본**, 자주 쓰는 데이터 로컬 캐시 | 로컬 스토리지 확장 |
| **Volume Gateway – Stored** | iSCSI | **로컬이 원본**, S3에 비동기 EBS 스냅샷 백업 | 저지연 로컬 + 클라우드 백업/DR |
| **Tape Gateway** | iSCSI VTL | 가상 테이프 → S3 → Glacier/Deep Archive | 기존 백업 소프트웨어(Veeam 등) 테이프 교체 |

- VM/하드웨어 어플라이언스/EC2로 배포. 온프레미스 "로컬처럼 보이되 데이터는 AWS에" 키워드.

#### AWS DataSync
- 에이전트(온프레미스 VM) 또는 에이전트리스(AWS↔AWS)로 **NFS, SMB, HDFS, S3 호환 객체** → **S3, EFS, FSx(모든 종류)** 전송. 10Gbps급, 증분, 스케줄링, 무결성 검증, 메타데이터/권한 보존, 대역폭 제한.
- "온프레미스 NAS를 EFS/FSx/S3로 **마이그레이션 또는 주기적 동기화**" → DataSync. (Storage Gateway는 **지속적 하이브리드 접근**, DataSync는 **전송**.)
- Direct Connect/VPN/인터넷 모두 가능, VPC 엔드포인트 지원.

#### AWS Transfer Family
- 관리형 **SFTP/FTPS/FTP/AS2** 엔드포인트 → S3 또는 EFS에 직접 저장. 사용자 인증(서비스 관리, AD, 커스텀 IdP(Lambda/API Gateway)), 고정 IP(VPC 엔드포인트 + EIP), 커스텀 도메인(Route 53).
- "파트너가 기존 SFTP 클라이언트로 업로드, 서버 관리 없이" 정답.

#### AWS Snow Family
| 장치 | 용량 | 특징 |
|---|---|---|
| Snowcone | 8TB HDD / 14TB SSD | 소형, DataSync 내장, 엣지 |
| Snowball Edge Storage Optimized | 80TB(~210TB) | 대량 전송, 로컬 S3 호환 스토리지 |
| Snowball Edge Compute Optimized | 28~42TB + GPU 옵션 | 엣지 EC2/Lambda 처리 |
| Snowmobile | 100PB(트럭) | 2024 종료, 구 문제에만 등장 |

- 판단 기준: 전송량/대역폭 계산. 예) 100Gbps 미만 회선으로 수백 TB 이상 → 주 단위 → Snowball. 대략 **10TB 초과 + 느린 회선 + 1주 이내 요구** → Snow. 데이터 도착 후 S3에 적재되며 Glacier로 바로 불가(수명주기로 이동).
- 암호화(KMS), 추적(SNS/콘솔), OpsHub GUI.

#### AWS Backup
- **중앙 집중 백업 정책**(백업 계획: 빈도, 보존, 수명주기 콜드 스토리지 이동) → EBS, EC2, RDS/Aurora, DynamoDB, EFS, FSx, S3, Storage Gateway, DocumentDB, Neptune, Redshift, VMware.
- **Backup Vault Lock**: WORM, 삭제 불가(규제). **크로스 리전/크로스 계정 복사**(Organizations 통합). 태그 기반 리소스 할당. 감사(Backup Audit Manager).
- "여러 서비스 백업을 하나의 정책으로, 규정 준수 보고" 정답.

#### AWS Elastic Disaster Recovery (DRS)
- 온프레미스/다른 클라우드/다른 리전 서버를 **블록 단위로 지속 복제**해 저비용 스테이징에 보관, 재해 시 분 단위로 EC2 시작. **RPO 초, RTO 분**. CloudEndure 후속. 드릴(테스트) 가능.
- DR 전략 비교: **Backup & Restore**(시간~일, 최저가) < **Pilot Light**(핵심 DB만 복제, 분~시간) < **Warm Standby**(축소 버전 상시, 분) < **Multi-site Active/Active**(실시간, 최고가).

### 시험 단골 시나리오

- 전 세계 지사에서 단일 S3 버킷으로 빠르게 대용량 업로드 → **S3 Transfer Acceleration + Multipart Upload**.
- 접근 패턴 예측 불가, 비용 최적화 자동 → **S3 Intelligent-Tiering**.
- 30일 뒤 거의 접근 안 하지만 즉시 복구 필요, 비용 절감 → **Standard-IA 전환(수명주기)**. 재생성 가능하면 One Zone-IA.
- 1개월 후 접근 없음, 무기한 보관, 최저 비용 → **Glacier Deep Archive 수명주기**.
- 분기 1회 아카이브 접근, 밀리초 복구 → **Glacier Instant Retrieval**.
- 규제로 N년간 누구도 삭제 불가 → **S3 Object Lock Compliance 모드**(버저닝 필수).
- 실수 삭제/덮어쓰기 복구 → **Versioning**(+ MFA Delete).
- 다른 리전에 복제해 DR/지연 감소 → **CRR**(기존 객체는 Batch Replication).
- 로그 집계를 같은 리전 다른 계정 버킷으로 → **SRR**.
- 암호화 키 사용 감사·로테이션 → **SSE-KMS**(KMS 요청 비용 ↓ → Bucket Key).
- 프라이빗 서브넷 EC2가 인터넷 없이 S3 접근 → **S3 Gateway Endpoint**(+ 버킷 정책 VPC 조건).
- 사용자에게 잠시 다운로드 허용 → **Presigned URL**.
- 다운로드 시 개인정보 마스킹 버전 제공, 복사본 없이 → **S3 Object Lambda**.
- 객체 일부만 조회해 전송량 절감 → **S3 Select** / **Byte-Range Fetch**.
- 초당 수만 요청 S3 성능 → **접두사 분산**(+ 병렬 요청).
- 정적 웹사이트 HTTPS + 커스텀 도메인 → **S3 + CloudFront(OAC) + ACM + Route 53**.
- EC2 DB 볼륨 IOPS 64,000 이상, 일관된 지연 → **io2 Block Express**.
- 비용 효율 범용 SSD, IOPS를 크기와 독립 설정 → **gp3**.
- 순차 대용량 로그/빅데이터, 저렴 → **st1**(최저가 sc1).
- 여러 EC2가 같은 EBS 공유(클러스터 FS) → **io1/io2 Multi-Attach**.
- 스냅샷에서 복원한 볼륨이 처음에 느림 → **Fast Snapshot Restore**.
- 다른 AZ/리전으로 볼륨 이동 → **스냅샷 → 복사 → 복원**.
- 암호화 안 된 볼륨 암호화 → **스냅샷 복사 시 암호화 → 새 볼륨**.
- 다중 AZ Linux 인스턴스 수백 대가 공유 파일시스템, 자동 확장 → **EFS**(비용 → IA 수명주기).
- Windows 앱 공유 드라이브 + AD 권한 → **FSx for Windows File Server**.
- HPC/ML 학습 데이터 S3에 있고 수백 GB/s 필요 → **FSx for Lustre(S3 연동)**.
- 온프레미스 NetApp 기능(스냅샷, SnapMirror, 다중 프로토콜) 유지 → **FSx for NetApp ONTAP**.
- 온프레미스 앱이 NFS/SMB로 S3를 로컬처럼 사용, 로컬 캐시 → **S3 File Gateway**.
- 온프레미스 iSCSI 블록, 로컬 저지연 + 클라우드 백업 → **Volume Gateway Stored**(로컬 확장이 목적이면 Cached).
- 테이프 백업 인프라를 클라우드로, 백업 소프트웨어 유지 → **Tape Gateway**.
- 온프레미스 NAS 수십 TB를 EFS/FSx/S3로 이전 또는 매일 동기화 → **DataSync**.
- 파트너가 SFTP로 파일 업로드, 서버 관리 없음 → **Transfer Family → S3**.
- 500TB를 1주 내 AWS로, 회선 느림 → **Snowball Edge**(여러 대).
- 네트워크 없는 현장에서 데이터 수집+전처리 → **Snowball Edge Compute Optimized / Snowcone**.
- EBS/RDS/DynamoDB/EFS 백업을 한 곳에서 정책·보존·규정 준수 → **AWS Backup**(+ Vault Lock, 크로스 리전).
- 온프레미스 서버 DR, RPO 초/RTO 분, 저비용 → **Elastic Disaster Recovery**.
- 대규모 데이터셋 공개하되 전송비는 사용자 부담 → **Requester Pays**.

## 05. Database & Analytics

> DB 문제는 "워크로드에 맞는 엔진 선택"과 "HA(Multi-AZ) vs 읽기 확장(Read Replica)" 두 축으로 정리된다.
> 수집된 문제에서 RDS 5위, DynamoDB 10위, Aurora 12위, Multi-AZ/Read Replica/ElastiCache/Athena/Glue/Redshift가 뒤를 잇는다.
> "관계형 + 관리형" → RDS/Aurora, "밀리초 key-value 무한 확장" → DynamoDB, "캐시/세션" → ElastiCache, "분석/OLAP" → Redshift, "S3 SQL 가끔" → Athena.

### 핵심 개념 상세

#### Amazon RDS
- 관리 범위: 프로비저닝, 패치, 백업, 복구, 모니터링은 AWS. OS/SSH 접근 불가(**RDS Custom**은 Oracle/SQL Server에 OS 접근 허용).
- **Multi-AZ (Instance)**: 다른 AZ에 **동기 복제 standby**. 장애/패치 시 **자동 장애 조치(1~2분, DNS 엔드포인트 동일)**. standby는 **읽기 불가**. 목적 = **가용성**.
- **Multi-AZ DB Cluster**: 1 writer + 2 reader(다른 AZ), 반동기, reader 읽기 가능, 장애 조치 ~35초. MySQL/PostgreSQL.
- **Read Replica**: **비동기** 복제, 최대 15개(엔진별 5~15), **같은 리전/다른 AZ/다른 리전**. 읽기 트래픽 분산, 분석 쿼리 오프로드. **승격(promote)** 가능(DR). 각 리플리카는 별도 엔드포인트(앱이 분기). 리플리카에 Multi-AZ 설정 가능. 리전 간 복제 데이터 전송 비용 있음. 목적 = **읽기 확장/DR**.
- **백업**: 자동 백업(보존 0~35일, 트랜잭션 로그 5분 단위 → **PITR**), 수동 스냅샷(무기한, 공유/복사 가능). 자동 백업은 인스턴스 삭제 시 함께 삭제(최종 스냅샷 옵션). **스냅샷을 다른 리전으로 복사**해 DR. 암호화 안 된 스냅샷 → 복사 시 암호화.
- **스토리지**: gp3/io1/io2, **Storage Auto Scaling**(임계치 도달 시 자동 증설, 최대 상한 설정). 증가만 가능.
- **암호화**: 생성 시 KMS 지정(나중에 켜려면 스냅샷 복사 암호화 후 복원). 전송 중 SSL/TLS 강제(파라미터 그룹 `rds.force_ssl`). **IAM DB 인증**(토큰 15분, MySQL/PostgreSQL) → 비밀번호 대신 IAM. **Secrets Manager 통합**으로 자격증명 자동 로테이션.
- **RDS Proxy**: 연결 풀링·다중화, 장애 조치 시간 최대 66% 단축, IAM 인증 강제. **Lambda/서버리스가 연결을 폭발시킬 때** 정답. VPC 내부에서만 접근.
- **모니터링**: **Performance Insights**(DB 부하/대기 이벤트, 쿼리별), **Enhanced Monitoring**(OS 메트릭, 1초 단위, 에이전트), CloudWatch(CPU/연결/IOPS).
- **유지 관리 창**, **파라미터 그룹**(엔진 설정), **옵션 그룹**(Oracle TDE 등), **Blue/Green Deployments**(스테이징 환경에서 업그레이드 후 스위치오버 1분 미만).
- **비용 절감**: RI, 테스트 DB는 **중지(최대 7일 후 자동 시작)** 또는 **스냅샷 후 삭제/복원**, 인스턴스 축소, Aurora Serverless.
- **RDS on Outposts**, **RDS for Db2**(2023~).

#### Amazon Aurora
- 스토리지: **3 AZ에 6개 복제본**(쓰기 4/6, 읽기 3/6 쿼럼), **10GB 단위 자동 확장 최대 128TB**, 자가 치유. 컴퓨트와 스토리지 분리.
- **리플리카 최대 15개**(Aurora Replica, 동일 스토리지 공유 → 복제 지연 ms), 자동 장애 조치 **30초 미만**(리플리카가 우선순위 티어로 승격). 리플리카 자체가 standby 역할(RDS처럼 별도 standby 불필요).
- **엔드포인트**: **Writer(Cluster)** / **Reader**(리플리카 간 로드밸런싱) / **Custom**(특정 리플리카 그룹, 예: 분석용 대형 인스턴스) / Instance.
- **Aurora Auto Scaling**: 리플리카 수를 CPU/연결 수 기반 자동 조절.
- **Aurora Serverless v2**: ACU 단위(0.5~256) 초 단위 자동 스케일, Multi-AZ·리플리카·Global DB 지원. 변동/간헐 워크로드, 개발/테스트. (v1은 레거시, 0까지 일시 중지 가능.)
- **Global Database**: 1 주 리전 + 최대 5 보조 리전(각 16 리플리카), **복제 지연 <1초**, **RPO 1초, RTO <1분**, 관리형 계획 장애 조치/스위치오버, 보조 리전 읽기(지연 감소). **Write Forwarding**으로 보조 리전 쓰기 전달.
- **Backtrack**(MySQL): 백업 복원 없이 최대 72시간 전으로 "되감기". **Cloning**: copy-on-write로 빠르고 저렴한 복제(테스트 환경). **Parallel Query**: 분석 쿼리를 스토리지 계층에서 병렬 처리. **Aurora ML**(SageMaker/Comprehend 호출), **Zero-ETL to Redshift**, **Aurora I/O-Optimized**(I/O 많을 때 비용 예측). **Database Activity Streams**(감사 → Kinesis).
- **Aurora Multi-Master**: 단종(v2/Global 권장). 구 문제에서 "다중 쓰기"는 Multi-Master 또는 DynamoDB Global Tables.
- 시험 포인트: "RDS MySQL 성능 5배, 가용성 극대화, 최소 관리" → Aurora. "예측 불가 간헐 트래픽" → Serverless v2. "글로벌 읽기 + 1분 미만 DR" → Global Database.

#### Amazon DynamoDB
- 완전 관리형, 서버리스, **밀리초 한 자릿수 일관 지연**, 무제한 처리량/스토리지, 다중 AZ 자동 복제, **항목 최대 400KB**(더 크면 S3에 저장하고 포인터).
- **키 설계**: **파티션 키**(해시, 고르게 분산되어야 함 → hot partition 방지) + 선택적 **정렬 키**(범위 쿼리). 접근 패턴 기준으로 설계(단일 테이블 디자인).
- **인덱스**: **LSI**(같은 파티션 키 + 다른 정렬 키, 테이블 생성 시만, 최대 5, 강한 일관성 가능) / **GSI**(다른 파티션/정렬 키, 언제든 추가, 최대 20, 자체 RCU/WCU, 최종 일관성만).
- **용량 모드**: **Provisioned**(RCU/WCU 지정 + Auto Scaling, 예측 가능 시 저렴, RI 가능) / **On-Demand**(요청당 과금, 예측 불가·급증, 관리 없음). 하루 1회 전환.
- **용량 단위 계산**: 1 **RCU** = 초당 **4KB 강한 일관성 읽기 1회** = 최종 일관성 2회 = 트랜잭션 0.5회. 1 **WCU** = 초당 **1KB 쓰기 1회**(트랜잭션 0.5회). 올림 처리.
  - 예: 6KB 항목을 초당 10회 강한 일관성 읽기 → 6KB→올림 8KB=2 단위 × 10 = **20 RCU**. 최종 일관성이면 10 RCU. 2.5KB 항목 초당 20회 쓰기 → 3 × 20 = **60 WCU**.
- **일관성**: 기본 **최종 일관성**(복제 ~1초), `ConsistentRead=true`로 **강한 일관성**(비용 2배, GSI 불가). **트랜잭션**(ACID, 최대 100항목, 비용 2배).
- **DAX**: 인메모리 캐시 클러스터(DynamoDB API 호환), 읽기 **마이크로초**, 코드 변경 최소. 읽기 집약·반복 조회. (ElastiCache는 집계 결과 등 범용 캐시.)
- **Streams**: 항목 변경 이력(24시간) → **Lambda 트리거**(변경 시 알림, 복제, 집계). **Kinesis Data Streams 연동**(장기 보존, 다수 소비자).
- **Global Tables**: 다중 리전 **active-active** 복제(Streams 필요), 1초 미만 지연, 마지막 쓰기 승리. 글로벌 저지연 + 리전 DR.
- **TTL**: 만료 시각 속성 → 자동 삭제(WCU 미소비, 48시간 내), 세션/로그 정리.
- **백업**: **PITR**(35일 초 단위), **On-demand 백업**, AWS Backup 통합. **Export to S3**(PITR 기반, RCU 미소비 → Athena 분석). **Import from S3**.
- **Standard-IA 테이블 클래스**: 드물게 접근, 스토리지 비용 60% 절감.
- **암호화** 기본(KMS), **IAM 세분화**(조건 `dynamodb:LeadingKeys`로 항목 수준), VPC 게이트웨이 엔드포인트.
- 시험 포인트: "스키마 유연, 밀리초, 자동 확장, 서버리스" → DynamoDB. "DynamoDB 읽기 마이크로초" → DAX. "변경 시 이벤트" → Streams + Lambda. "다중 리전 읽기/쓰기" → Global Tables. "세션 데이터 자동 만료" → TTL.

#### Amazon ElastiCache
| | Redis (OSS/Valkey) | Memcached |
|---|---|---|
| 데이터 구조 | 문자열, 해시, 리스트, 셋, 정렬 셋, 지리, 스트림 | 문자열(단순 key-value) |
| HA | 복제본, **Multi-AZ 자동 장애 조치**, 클러스터 모드(샤딩) | 없음(노드 독립), 멀티스레드 |
| 영속성 | 스냅샷(RDB)/AOF, 백업·복원 | 없음 |
| 기능 | Pub/Sub, Lua, 트랜잭션, **정렬 셋 → 리더보드**, Global Datastore(리전 간 복제) | 단순 캐시, 수평 분할 쉬움 |
| 선택 | 거의 모든 경우(복잡 구조, 영속, HA) | 단순 캐시 최대 성능, 멀티스레드 |

- **Serverless 모드**(2023~): 용량 관리 없음.
- **캐싱 전략**: **Lazy Loading**(캐시 미스 시 DB 조회 후 적재, 오래된 데이터 가능) / **Write-Through**(쓰기마다 캐시 갱신, 읽기 지연 없음, 쓰기 부하↑) / **TTL**로 만료.
- **세션 저장**: ELB sticky session 대신 Redis에 세션 → 무상태 서버, 스케일 자유. DynamoDB도 가능.
- **보안**: Redis AUTH/RBAC, 전송·저장 암호화, IAM 인증(Redis 7+), VPC 내부만.
- 시험 포인트: "DB 읽기 부하 줄이기, 자주 읽는 데이터" → ElastiCache. "게임 리더보드 실시간" → Redis Sorted Set. "세션 상태 공유" → Redis. "복잡 구조 없이 가장 단순한 캐시" → Memcached.

#### Amazon MemoryDB for Redis
- Redis 호환이면서 **내구성 있는 기본 데이터베이스**(다중 AZ 트랜잭션 로그), 마이크로초 읽기/밀리초 쓰기. "캐시+DB를 하나로, 데이터 손실 없이" 정답. ElastiCache는 캐시(데이터 손실 허용).

#### Amazon Redshift
- **컬럼형 MPP OLAP**, PB급, 표준 SQL/JDBC/ODBC, BI 연동. 단일 AZ 클러스터(Multi-AZ 옵션 RA3). 리더 노드 + 컴퓨트 노드.
- **RA3 노드**: 컴퓨트/스토리지 분리(관리형 스토리지), **데이터 공유(Data Sharing)**. DC2: 로컬 SSD.
- **Redshift Spectrum**: S3 데이터를 로드 없이 외부 테이블로 쿼리(Glue Catalog). **Federated Query**: RDS/Aurora 직접 쿼리.
- **Redshift Serverless**: 클러스터 관리 없음, 사용량 과금. 간헐/예측 불가 분석.
- **Concurrency Scaling**: 동시 쿼리 급증 시 임시 클러스터 자동 추가. **WLM**: 큐/우선순위. **Materialized View**, **AQUA**, **Zero-ETL**(Aurora→Redshift).
- **스냅샷**: 자동/수동, **크로스 리전 자동 복사**(DR). **Enhanced VPC Routing**: S3 COPY/UNLOAD 트래픽을 VPC 내부로.
- 로딩: **COPY from S3**(병렬, 권장), Firehose, DMS. 분산 키/정렬 키 설계.
- 시험 포인트: "복잡한 분석 쿼리, PB, BI" → Redshift. "S3 데이터를 로드 없이 Redshift에서 조인" → Spectrum. "가끔 분석, 관리 없이" → Serverless 또는 Athena.

#### 특수 목적 DB
- **Neptune**: 그래프(소셜 네트워크, 추천, 사기 탐지, 지식 그래프). Gremlin/openCypher/SPARQL. 리플리카 15, Multi-AZ. **Neptune ML**.
- **DocumentDB**: MongoDB 호환 JSON 문서 DB, 3 AZ 6 복제(Aurora식), 리플리카 15, Global Cluster. "MongoDB 워크로드를 관리형으로".
- **Keyspaces**: Cassandra(CQL) 호환 서버리스. "Cassandra 앱을 코드 변경 없이".
- **QLDB**: 불변·암호학적 검증 가능 원장, 중앙 소유(블록체인은 **Managed Blockchain**). 금융 거래 이력, 공급망.
- **Timestream**: 시계열(IoT 센서, DevOps 메트릭), 자동 메모리→자기 티어링, 시계열 함수. (Timestream for InfluxDB도 추가.)
- **OpenSearch Service**: 전문 검색, 로그 분석(CloudWatch Logs/Firehose 연동), OpenSearch Dashboards. 다중 AZ, 전용 마스터, UltraWarm/Cold 티어. **Serverless** 옵션. DynamoDB와 Zero-ETL. "로그 대시보드/텍스트 검색" 정답.

#### 마이그레이션: DMS & SCT
- **DMS**: 소스→대상 복제. **동종**(Oracle→Oracle) 또는 **이종**(Oracle→Aurora PostgreSQL; **SCT**로 스키마 먼저 변환). **복제 인스턴스**(EC2) 또는 **DMS Serverless**. 모드: 전체 로드 / **전체 로드 + CDC(지속 복제)** / CDC만. 소스 DB 가동 유지(최소 다운타임). 소스/대상: 온프레미스, EC2, RDS, Aurora, S3, DynamoDB, Redshift, Kinesis, DocumentDB, OpenSearch 등. 데이터 검증 기능. **Schema Conversion**이 DMS에 통합(2023).
- **SCT**: 스키마·저장 프로시저·코드 변환 + 평가 보고서. 데이터 웨어하우스(Teradata/Netezza→Redshift)도. Snowball Edge와 연계해 대용량 오프라인 이전.
- **Oracle/SQL Server → 오픈소스**로 라이선스 절감 문제 단골: SCT로 변환 → DMS로 이전(CDC로 컷오버).
- **RDS 스냅샷/MySQL 덤프/Percona XtraBackup → S3 → Aurora 복원**: 대용량 MySQL 이전 시 빠름.

#### 분석 서비스
- **Athena**: S3 위 **서버리스 SQL(Presto/Trino)**, **스캔 데이터 TB당 과금** → **파티셔닝(날짜 등), 컬럼 포맷(Parquet/ORC), 압축**으로 비용·성능 개선. Glue Data Catalog 사용. **Federated Query**(Lambda 커넥터로 RDS/DynamoDB 등). CloudTrail/VPC Flow/ELB 로그 분석 단골. "S3 로그를 가끔 SQL로, 인프라 없이, 최소 변경" 정답.
- **Glue**: 서버리스 **ETL**(Spark/Python 작업, 북마크로 증분), **Crawler**(스키마 자동 발견 → **Data Catalog**), **Glue Studio/DataBrew**(코드 없는 정제), **Glue Streaming**. Catalog는 Athena·Redshift Spectrum·EMR·Lake Formation의 공통 메타스토어.
- **EMR**: Hadoop/Spark/Hive/Presto/HBase 클러스터. 마스터/코어/**태스크 노드(Spot 권장)**, EMRFS(S3), 임시 클러스터(작업 후 종료). EMR Serverless, EMR on EKS. "기존 Spark/Hadoop 코드 대규모 실행".
- **Lake Formation**: S3 데이터 레이크 구축/권한 중앙화(**행/열/셀 수준**, 태그 기반 LF-Tags), Athena/Redshift/EMR/QuickSight에 일관 적용. Blueprint로 수집 자동화.
- **QuickSight**: 서버리스 BI, **SPICE** 인메모리, ML 인사이트, 임베딩, **행 수준 보안(RLS)**, 사용자·그룹·IAM Identity Center 공유(IAM 역할 공유 아님). Enterprise 에디션에 VPC 연결/RLS/AD.
- **Kinesis/Firehose/MSK**는 Serverless 노트, **OpenSearch**는 위 참고.
- 전형적 파이프라인: 소스 → Firehose/DMS/DataSync → **S3(Raw)** → Glue ETL → **S3(Parquet, 파티션)** → Athena/Redshift Spectrum → QuickSight.

### 시험 단골 시나리오

- RDS 읽기 부하 분산, 보고서 쿼리 분리 → **Read Replica**(앱이 읽기 엔드포인트 사용).

- 기존 RDS를 암호화 → **스냅샷 → 암호화 복사 → 복원**.
- 특정 시점(어제 14:05)으로 복구 → **자동 백업 PITR**(보존 기간 내).
- 다른 리전 DR → **크로스 리전 Read Replica** 또는 **스냅샷 복사**(Aurora면 Global Database).
- 월 1회 48시간만 쓰는 테스트 RDS 비용 절감 → **스냅샷 후 삭제, 필요 시 복원**(중지는 7일 제한).

- 읽기 트래픽 예측 불가, 자동으로 리플리카 수 조절 → **Aurora Auto Scaling**.
- 간헐적/개발 DB, 사용량에 따라 자동 스케일 → **Aurora Serverless v2**.
- 전 세계 사용자 저지연 읽기 + RPO 1초 RTO 1분 DR → **Aurora Global Database**.
- 실수로 삭제한 테이블을 몇 시간 전으로 되돌리기(복원 없이) → **Aurora Backtrack**.
- 프로덕션 복제본으로 빠르게 테스트 환경 → **Aurora Cloning**.
- 밀리초 지연, 무한 확장, 스키마 유연, 서버리스 key-value → **DynamoDB**.
- DynamoDB 읽기 마이크로초, 코드 변경 최소 → **DAX**.
- DynamoDB 항목 변경 시 Lambda로 후처리 → **DynamoDB Streams + Lambda**.
- 다중 리전 활성-활성 key-value → **Global Tables**.
- 세션/임시 데이터 자동 삭제 → **TTL**.
- 트래픽 급증 예측 불가, 용량 관리 없이 → **On-Demand 모드**.
- 핫 파티션/스로틀링 → **파티션 키 재설계(카디널리티 높게, 샤딩 접미사)**, GSI 분리.
- 게임 리더보드 실시간 순위 → **ElastiCache Redis Sorted Set**.
- 웹 세션 공유로 무상태 서버 → **ElastiCache Redis**(또는 DynamoDB).
- 캐시이면서 데이터 손실 불가 기본 DB → **MemoryDB**.
- PB급 분석, 복잡 조인, BI 도구 → **Redshift**; S3 데이터 로드 없이 → **Spectrum**; 동시 사용자 급증 → **Concurrency Scaling**.
- S3의 JSON/CSV 로그를 가끔 SQL로 조회, 인프라 없음 → **Athena**(비용 ↓ → Parquet+파티션).
- 데이터 레이크 스키마 자동 발견, ETL 서버리스 → **Glue Crawler + Glue ETL**.
- 열/행 수준 데이터 레이크 권한 중앙 관리 → **Lake Formation**.
- 경영진만 전체 대시보드, 나머지 제한 → **QuickSight 대시보드를 사용자/그룹에 공유(+ RLS)**.
- 온프레미스 Oracle → Aurora PostgreSQL, 다운타임 최소 → **SCT(스키마) + DMS(전체 로드+CDC)**.
- MongoDB 앱을 관리형으로 → **DocumentDB**. Cassandra → **Keyspaces**. 소셜 그래프 → **Neptune**. 변경 불가 거래 원장 → **QLDB**. IoT 시계열 → **Timestream**. 로그 전문 검색/대시보드 → **OpenSearch**.

## 06. Network & Content Delivery

> 네트워크 문제는 VPC 기본 구조(서브넷/라우팅/IGW/NAT), 보안 계층(SG vs NACL), 연결(Direct Connect/VPN/Peering/Transit Gateway/PrivateLink), 엣지(CloudFront/Global Accelerator/Route 53)로 나뉜다.

### 핵심 개념 상세

#### VPC 기본 구조
- **CIDR**: /16 ~ /28. 보조 CIDR 추가 가능. 피어링/VPN 대상과 **겹치면 안 됨**. 각 서브넷은 **5개 IP 예약**(네트워크, 라우터, DNS, 미래, 브로드캐스트) → /24에 251개 사용.
- **서브넷**: **하나의 AZ**에 속함. **퍼블릭** = 라우팅 테이블에 `0.0.0.0/0 → IGW`가 있는 서브넷(+ 공인 IP 자동 할당). **프라이빗** = IGW 경로 없음(NAT로 아웃바운드만).
- **라우팅 테이블**: 서브넷당 1개(기본 라우팅 테이블 상속). 로컬 경로(VPC CIDR)는 삭제 불가. 가장 구체적 경로 우선.
- **Internet Gateway**: VPC당 1개, 수평 확장, 공인 IP↔프라이빗 IP NAT 수행. **Egress-only IGW**: IPv6 아웃바운드 전용.
- **DNS**: `enableDnsSupport`, `enableDnsHostnames` 둘 다 켜야 퍼블릭 DNS 이름과 프라이빗 호스티드 존 동작. Route 53 Resolver(.2 주소).
- **기본 VPC**: 리전마다 172.31.0.0/16, 퍼블릭 서브넷 AZ별.
- **IPv6**: AWS 할당 /56, 모두 공인. 듀얼스택. **IPAM**으로 조직 CIDR 관리.
- **3계층 설계 정석**: 퍼블릭 서브넷(ALB, NAT, Bastion) / 프라이빗 앱 서브넷(EC2/ECS) / 프라이빗 DB 서브넷(RDS), 각 계층을 **2개 이상 AZ**에.

#### NAT Gateway vs NAT Instance
| | NAT Gateway | NAT Instance |
|---|---|---|
| 관리 | AWS 관리형, 자동 확장(5~100Gbps) | 사용자 EC2, 사이즈/패치 책임 |
| HA | **AZ 단위** → AZ마다 하나씩 두고 각 프라이빗 서브넷 라우팅 | 스크립트로 장애 조치 |
| SG | 없음(NACL만) | SG 적용 가능 |
| 용도 | 기본 정답 | 저비용 테스트, 포트 포워딩, Bastion 겸용 |

- NAT Gateway는 **퍼블릭 서브넷**에 두고 **Elastic IP** 필요. 프라이빗 서브넷 라우팅 `0.0.0.0/0 → nat-xxx`. **AZ 장애 내성 = AZ마다 NAT 게이트웨이**(한 AZ의 NAT를 다른 AZ 서브넷이 쓰면 그 AZ 장애 시 끊김 + 리전 내 데이터 전송 비용).
- **Private NAT Gateway**: 겹치는 CIDR 네트워크 간 통신(인터넷 아님).
- NAT 비용 절감: S3/DynamoDB 트래픽은 **게이트웨이 엔드포인트**로 돌리기(무료), 기타 AWS 서비스는 인터페이스 엔드포인트.

#### Security Group vs Network ACL
| | Security Group | Network ACL |
|---|---|---|
| 적용 | ENI/인스턴스 | 서브넷 |
| 상태 | **Stateful**(응답 자동 허용) | **Stateless**(인바운드/아웃바운드 둘 다 규칙, 에페메럴 포트 1024-65535 열어야) |
| 규칙 | **허용만**(기본 모두 거부) | 허용+**거부**, 번호 낮은 순 평가(첫 매칭) |
| 기본값 | 인바운드 거부, 아웃바운드 허용 | 기본 NACL 모두 허용, 커스텀 NACL 모두 거부 |
| 소스 | CIDR, **다른 SG 참조**, 접두사 목록 | CIDR만 |
| 용도 | 계층 간 접근(웹 SG→앱 SG→DB SG) | 특정 IP **차단**, 서브넷 방어 |

- "특정 공격 IP 차단" → **NACL Deny**(SG는 거부 불가) 또는 WAF IP set.
- "DB는 앱 서버에서만 접근" → DB SG 인바운드 소스 = **앱 SG ID**(IP 대신).
- 다중 계층 보안: SG + NACL + WAF + Network Firewall + Shield.

#### VPC Endpoint / PrivateLink
- **Gateway Endpoint**: **S3, DynamoDB**만. 라우팅 테이블에 접두사 목록 경로 추가. **무료**. 같은 리전만. 엔드포인트 정책 + 버킷 정책 `aws:sourceVpce`로 잠금. 온프레미스/피어링 VPC에서는 사용 불가(인터페이스 엔드포인트 필요).
- **Interface Endpoint(PrivateLink)**: 서브넷에 **ENI + 프라이빗 IP**, SG 적용, 프라이빗 DNS(서비스 DNS가 프라이빗 IP로 해석). 대부분의 AWS 서비스(S3도 가능: 온프레미스에서 DX/VPN으로 S3 접근 시), SaaS, 자체 서비스. 시간당 + GB 과금. 온프레미스/피어링에서도 접근 가능.
- **PrivateLink로 자체 서비스 노출**: 공급자 VPC **NLB**(또는 GWLB) → Endpoint Service → 소비자 VPC Interface Endpoint. 수천 소비자, CIDR 겹쳐도 됨, 소비자→공급자 단방향, 피어링보다 안전/확장. "SaaS를 다른 계정 고객에게 프라이빗하게 제공" 정답.
- 시험 포인트: "프라이빗 서브넷 EC2가 인터넷/NAT 없이 S3" → Gateway Endpoint. "KMS/SQS/ECR 프라이빗 접근" → Interface Endpoint. "NAT 비용 급증, 대부분 S3 트래픽" → Gateway Endpoint.

#### VPC 간 / 하이브리드 연결
- **VPC Peering**: 1:1, **전이 불가**(A-B, B-C여도 A-C 불가 → 각각 피어링), CIDR 겹침 불가, 양쪽 라우팅 테이블 수정, SG 참조 가능(같은 리전), 리전/계정 간 가능. 소수 VPC.
- **Transit Gateway**: 리전 허브. VPC, VPN, Direct Connect Gateway, 피어링(리전 간)을 어태치먼트로. **전이 라우팅**, TGW 라우팅 테이블로 세분화(프로덕션/개발 격리), **멀티캐스트**, 중앙 아웃바운드(공유 NAT/Network Firewall), Organizations 공유(RAM). 수십~수천 VPC 또는 "온프레미스와 여러 VPC를 단순하게" 정답. 과금(어태치먼트 시간 + 데이터).
- **Site-to-Site VPN**: VGW(또는 TGW) ↔ Customer Gateway, **IPsec 터널 2개**(HA), 터널당 ~1.25Gbps, 인터넷 경유(변동 지연), 분 단위 구축. **ECMP**(TGW)로 다중 터널 대역폭 합산. **Accelerated VPN**(Global Accelerator). DX의 백업 또는 암호화 레이어.
- **Direct Connect**: AWS DX 로케이션에 **전용 연결**(1/10/100/400Gbps) 또는 파트너 **호스팅 연결**(50Mbps~). **구축 수주~수개월**. 일관된 낮은 지연, 대역폭, 데이터 전송 비용 ↓. **기본적으로 암호화 없음** → DX 위에 **VPN** 또는 **MACsec**(10/100G). **VIF**: Private VIF(VPC/VGW), Public VIF(S3 등 퍼블릭 서비스), Transit VIF(TGW via DX Gateway). **DX Gateway**: 하나의 DX로 여러 리전 VPC. **LAG**: 링크 집계. **HA**: 두 로케이션에 두 DX(최대 복원력) 또는 DX + VPN 백업. **Resilience Toolkit** 설계 모델.
- **Client VPN**: 원격 사용자 → VPC(및 온프레미스), 인증(AD/인증서/SAML), 분할 터널.
- **VPC Lattice**: 서비스 간 애플리케이션 계층 네트워킹(신규, 드묾).
- 시험 포인트: "다음 주까지 온프레미스 연결" → VPN. "안정적 대역폭, 일관 지연, 대용량 지속 전송" → Direct Connect(+VPN 암호화/백업). "VPC 50개 + 온프레미스 전부 연결" → Transit Gateway. "VPC 2개 저비용 연결" → Peering.

#### Amazon Route 53
- **호스티드 존**: Public / **Private**(VPC 내부 DNS, 여러 VPC 연결). 도메인 등록도 가능. 100% SLA.
- **레코드**: A/AAAA/CNAME/MX/TXT/NS/SOA/SRV/PTR/CAA. **Alias 레코드**: AWS 리소스(ALB, CloudFront, S3 웹사이트, API Gateway, Global Accelerator, 다른 Route 53 레코드)를 **zone apex(example.com)에도** 가리킴, 무료, 헬스체크 연동. **CNAME은 apex 불가, 유료 쿼리**.
- **라우팅 정책**
  - **Simple**: 단일 리소스(여러 값이면 랜덤), 헬스체크 없음.
  - **Weighted**: 비율 분배(블루/그린, 카나리, A/B). 0이면 제외.
  - **Latency**: 사용자에게 지연 최소 리전.
  - **Failover**: Primary 헬스 실패 시 Secondary(active-passive DR). 예: ALB → S3 정적 페이지.
  - **Geolocation**: 사용자 **위치**(대륙/국가/미국 주) 기준 → 콘텐츠 현지화, 규제. Default 레코드 필수.
  - **Geoproximity**: 리소스 위치 + **bias**로 영역 조절(Traffic Flow 필요).
  - **Multivalue Answer**: 최대 8개 정상 레코드 반환(간이 로드밸런싱, 헬스체크 ✓).
  - **IP-based**: 클라이언트 CIDR 기준.
- **헬스체크**: 엔드포인트(HTTP/HTTPS/TCP, 글로벌 체커, 2xx/3xx 또는 본문 문자열), 계산된(다른 헬스체크 조합), **CloudWatch 알람 기반**(프라이빗 리소스는 직접 체크 불가 → 알람으로). 장애 조치의 핵심.
- **Route 53 Resolver**: **Inbound Endpoint**(온프레미스 → VPC 프라이빗 존 조회), **Outbound Endpoint + 규칙**(VPC → 온프레미스 DNS 조회). 하이브리드 DNS 정답. **DNS Firewall**: 도메인 차단.
- **Application Recovery Controller**: 리전 장애 조치 준비 상태 점검/라우팅 제어.
- **TTL**: 낮추면 전환 빠름, 쿼리 비용 ↑. 마이그레이션 전 TTL 낮추기.
- 시험 포인트: "apex 도메인을 ALB로" → Alias A. "가장 가까운 리전" → Latency. "국가별 다른 콘텐츠/법규" → Geolocation. "DR 자동 전환" → Failover + 헬스체크. "온프레미스에서 VPC 내부 DNS" → Resolver Inbound.

#### Amazon CloudFront
- 전 세계 **엣지 로케이션 + 리전 엣지 캐시**에서 콘텐츠 캐시/전송. **오리진**: S3(정적), ALB/EC2/API Gateway(동적), MediaStore, 모든 HTTP 서버, 다중 오리진 + **오리진 그룹(장애 조치)**.
- **S3 보안**: **OAC(Origin Access Control)**(OAI 후속)로 CloudFront만 S3 접근, 버킷은 비공개. 정적 사이트 HTTPS+커스텀 도메인(**ACM 인증서는 us-east-1**).
- **캐시 제어**: Cache Policy(키: 헤더/쿠키/쿼리, TTL), Origin Request Policy, Response Headers Policy. **Invalidation**(경로별 무효화, 월 1,000개 무료) 또는 **버전 파일명**. TTL 기본 24h.
- **동적 콘텐츠 가속**: 캐시 안 해도 AWS 백본·연결 재사용·TLS 종료로 빨라짐. ALB 오리진 앞에 CloudFront를 두는 것이 "전역 정적+동적 가속" 정답.
- **프라이빗 콘텐츠**: **Signed URL**(개별 파일, RTMP) / **Signed Cookie**(다수 파일, URL 변경 없음), **Trusted Key Group**. S3 Presigned URL과 혼동 주의(CloudFront 경유 시 Signed URL).
- **지리 제한(Geo Restriction)**: 국가 허용/차단(라이선스).
- **보안**: HTTPS 강제(Viewer Protocol Policy), 오리진 커스텀 헤더(ALB가 CloudFront 경유만 허용), **WAF**, **Shield Standard 자동**, **Field-level Encryption**(민감 필드 공개키 암호화). ALB SG에 CloudFront **관리형 접두사 목록**만 허용.
- **엣지 컴퓨팅**: **CloudFront Functions**(JS, 밀리초 미만, 뷰어 요청/응답만, 헤더 조작/URL 리라이트/간단 인증, 초저비용) vs **Lambda@Edge**(Node/Python, 뷰어+오리진 요청/응답 4곳, 수 ms~초, 네트워크 호출·본문 접근, 복잡 로직/A-B/이미지 처리). us-east-1에서 배포.
- **Origin Shield**: 추가 중앙 캐시 계층으로 오리진 부하 ↓.
- **가격 클래스**: 엣지 범위 제한으로 비용 절감(Price Class 100/200/All).
- 시험 포인트: "전 세계 사용자 지연 감소, S3+ALB 콘텐츠" → CloudFront(오리진 2개). "S3를 CloudFront로만 접근" → OAC + 버킷 정책. "유료 구독자만 동영상" → Signed URL/Cookie. "국가 차단" → Geo Restriction. "헤더 간단 조작" → CloudFront Functions.

#### AWS Global Accelerator
- **Anycast 고정 IP 2개**(또는 BYOIP) → 가장 가까운 엣지 → **AWS 글로벌 백본** → 리전 엔드포인트(ALB, NLB, EC2, EIP). **TCP/UDP** 모두, 캐시 없음. 엔드포인트 가중치, **트래픽 다이얼**(리전별 비율), **헬스체크 기반 즉시 장애 조치(초 단위, DNS 캐시 영향 없음)**, 클라이언트 IP 보존, Shield Standard.
- **vs CloudFront**: CloudFront = HTTP 캐시/콘텐츠 전송. GA = **비HTTP(게임 UDP, VoIP, IoT MQTT)**, **고정 IP 필요(화이트리스트)**, **빠른 리전 장애 조치**, 동적 TCP 앱. 둘 다 엣지 네트워크 사용.
- 시험 포인트: "UDP 게임/VoIP 글로벌 지연 최소 + 리전 자동 장애 조치" → Global Accelerator(+NLB). "고객 방화벽에 고정 IP 등록 필요, 멀티 리전" → GA.

#### 엣지 보안: WAF / Shield / Firewall Manager / Network Firewall
- **WAF**: Web ACL(규칙: IP set, 지역, 속도 기반(DDoS L7/무차별 대입), SQLi/XSS, 크기 제한, 헤더/본문 패턴, 봇 제어, **관리형 규칙 그룹**(OWASP 등)). 연결 대상: **CloudFront, ALB, API Gateway, AppSync, Cognito, App Runner, Verified Access**. **NLB 불가**. 로그 → Kinesis Firehose/S3/CloudWatch.
- **Shield Standard**: 무료, 모든 고객, L3/L4 DDoS(SYN flood, UDP reflection). **Shield Advanced**: 월 $3,000, EC2/ELB/CloudFront/Global Accelerator/Route 53 보호, **DDoS Response Team(DRT)** 24/7, **비용 보호(DDoS 스케일링 비용 환급)**, L7 탐지, WAF 자동 완화, 고급 보고. "DDoS 대응 전문 팀과 비용 보호" 키워드.
- **Firewall Manager**: Organizations 전체 계정에 WAF/Shield Advanced/SG/Network Firewall/Route 53 DNS Firewall 정책 자동 적용(신규 리소스 포함). "여러 계정에 일관된 WAF 규칙" 정답.
- **Network Firewall**: VPC 경계(IGW/NAT/VPN/DX/TGW 사이)에 상태 저장/비저장 규칙, **도메인 기반 아웃바운드 필터링**, **IPS(Suricata)**, 수만 규칙, 중앙 검사 VPC(TGW) 패턴. "온프레미스 검사 서버와 동일한 트래픽 흐름 검사/필터링을 AWS에서" 정답. 서드파티 어플라이언스를 쓰면 GWLB.
- **GuardDuty/Inspector/Macie**는 보안 노트 참고.

#### 기타 네트워크 기능
- **ENI**: 보조 ENI를 다른 인스턴스로 옮겨 **MAC/IP 유지 장애 조치**(라이선스 바인딩). 보조 프라이빗 IP. ENA/EFA.
- **Elastic IP**: 실행 중 인스턴스에 연결 시 무료, 미연결/추가 EIP 과금. 인스턴스 중지해도 유지(일반 공인 IP는 바뀜).
- **VPC Flow Logs**: ENI/서브넷/VPC 단위, ACCEPT/REJECT 메타데이터(페이로드 ✗) → CloudWatch Logs/S3/Firehose. **Athena로 분석**. "SG/NACL이 트래픽을 막는지 확인" 정답. 일부 트래픽(DNS to Resolver, DHCP, 메타데이터) 제외.
- **Traffic Mirroring**: 실제 패킷 복제 → NLB/ENI(IDS). Flow Logs와 구분.
- **Reachability Analyzer**: 소스→대상 경로 가능 여부와 막는 구성 요소. **Network Access Analyzer**: 의도치 않은 인터넷 노출 발견.
- **Bastion Host**: 퍼블릭 서브넷 점프 서버 → 권장 대안 **Systems Manager Session Manager**(인바운드 포트 없음, IAM, 로깅) 또는 **EC2 Instance Connect Endpoint**.
- **AWS Network Manager / Cloud WAN**: 글로벌 네트워크 중앙 관리(드묾).

### 시험 단골 시나리오

- 프라이빗 서브넷 인스턴스가 인터넷으로 패치 다운로드, 인바운드 차단 → **퍼블릭 서브넷 NAT Gateway + 프라이빗 라우팅**.
- NAT Gateway 단일 장애점 제거 → **AZ마다 NAT Gateway, 서브넷별 라우팅**.
- 프라이빗 EC2 → S3/DynamoDB, 인터넷·NAT 없이 무료 → **Gateway Endpoint**(+ 버킷 정책 `aws:sourceVpce`).
- 프라이빗 EC2 → SQS/KMS/Secrets Manager/ECR 프라이빗 접근 → **Interface Endpoint**.
- 온프레미스에서 DX/VPN으로 S3 프라이빗 접근 → **S3 Interface Endpoint**(게이트웨이는 온프레미스 불가) 또는 Public VIF.
- 다른 계정/VPC 고객에게 서비스를 프라이빗 노출, CIDR 겹침, 수백 고객 → **PrivateLink(NLB + Endpoint Service)**.
- VPC 2개 프라이빗 통신 → **VPC Peering**(양쪽 라우팅+SG). 3개 이상 전부 연결/온프레미스 포함 → **Transit Gateway**.
- A-B, B-C 피어링인데 A-C 통신 안 됨 → 피어링은 **전이 불가** → A-C 직접 피어링 또는 TGW.
- 온프레미스 연결을 며칠 내 저비용으로 → **Site-to-Site VPN**(터널 2개).
- 온프레미스 대용량 지속 전송, 일관된 지연 → **Direct Connect**; 암호화 필요 → **DX 위 VPN** 또는 MACsec; HA → **두 번째 DX 또는 VPN 백업**.
- 여러 리전 VPC를 하나의 DX로 → **Direct Connect Gateway**(+TGW).
- 특정 IP/대역 차단 → **NACL Deny** 또는 **WAF IP set**(SG는 불가).
- DB는 웹 계층에서만 접근 → **DB SG 소스 = 웹/앱 SG**.
- 트래픽이 막히는 원인 파악 → **VPC Flow Logs(REJECT)** / **Reachability Analyzer**.
- IDS에 실제 패킷 전달 → **Traffic Mirroring**.
- 온프레미스 방화벽/IDS와 같은 검사·필터링을 VPC에, 관리형 → **AWS Network Firewall**; 서드파티 어플라이언스 → **GWLB**.
- apex 도메인(example.com)을 ALB/CloudFront로 → **Route 53 Alias**.
- 사용자를 지연 최소 리전으로 + 리전 장애 시 자동 전환 → **Latency 라우팅 + 헬스체크**(또는 Global Accelerator).
- 신규 버전에 10% 트래픽 → **Weighted** 라우팅(또는 ALB 가중 대상 그룹).
- 국가별 콘텐츠/법규 → **Geolocation**; EU 사용자만 EU 리전 → Geolocation.
- 프라이머리 장애 시 S3 정적 "점검 중" 페이지 → **Failover 라우팅 + S3 웹사이트 Alias**.
- 온프레미스 서버가 VPC 프라이빗 DNS 이름 조회 → **Route 53 Resolver Inbound Endpoint**; 반대 → **Outbound Endpoint + 전달 규칙**.
- 전 세계 사용자에게 S3 정적 + ALB 동적 콘텐츠 빠르게 → **CloudFront(오리진 2개) + Route 53**.
- S3 버킷을 CloudFront로만 접근 → **OAC + 버킷 정책**(퍼블릭 차단 유지).
- 정적 사이트 HTTPS 커스텀 도메인 → **CloudFront + ACM(us-east-1) + Route 53 Alias**.
- 유료 회원만 미디어 다운로드 → **CloudFront Signed URL/Cookie**; 단일 파일 임시 공유 → S3 Presigned URL.
- 특정 국가에서 콘텐츠 차단(라이선스) → **CloudFront Geo Restriction**.
- 요청 헤더 기반 간단 리다이렉트/리라이트, 최저 지연·비용 → **CloudFront Functions**; 오리진 요청 시 외부 호출/복잡 로직 → **Lambda@Edge**.
- ALB가 CloudFront를 통해서만 트래픽 받도록 → **커스텀 오리진 헤더 검증 + SG에 CloudFront 접두사 목록**.
- UDP/TCP 게임·VoIP 글로벌 지연 최소 + 고정 IP + 즉시 장애 조치 → **Global Accelerator + NLB**.
- 고객 방화벽 화이트리스트용 고정 IP로 멀티 리전 ALB 접근 → **Global Accelerator**.
- SQL 인젝션/XSS/속도 제한 → **WAF**(CloudFront/ALB/API Gateway). NLB에는 불가.
- DDoS 대응 팀, 비용 보호, L7 → **Shield Advanced**.
- 조직 전 계정에 WAF 규칙·SG 정책 자동 적용 → **Firewall Manager**.
- Bastion 없이 프라이빗 EC2 셸 접근, 포트 개방 없이, 감사 → **SSM Session Manager**.
- 인스턴스 장애 시 MAC/IP 유지해 라이선스 서버 이전 → **보조 ENI 이동**.

### 자주 헷갈리는 비교

#### CloudFront vs Global Accelerator
| | CloudFront | Global Accelerator |
|---|---|---|
| 계층 | HTTP/HTTPS | TCP/UDP(모든 앱) |
| 캐시 | ✓ 엣지 캐시 | ✗ (프록시) |
| IP | 변동(도메인) | **고정 Anycast IP 2개** |
| 장애 조치 | 오리진 그룹 | 헬스체크 즉시(초), DNS 무관 |
| 용도 | 정적/동적 웹, 미디어, API | 게임, VoIP, IoT, 비HTTP, 고정 IP, 멀티 리전 |

#### Gateway vs Interface Endpoint
| | Gateway | Interface(PrivateLink) |
|---|---|---|
| 서비스 | S3, DynamoDB | 대부분 + SaaS + 자체 |
| 구현 | 라우팅 테이블 | ENI + 프라이빗 IP + SG |
| 비용 | 무료 | 시간+GB |
| 온프레미스/피어링 접근 | ✗ | ✓ |

#### Peering vs Transit Gateway vs PrivateLink
| | Peering | Transit Gateway | PrivateLink |
|---|---|---|---|
| 토폴로지 | 1:1 | 허브-스포크 | 서비스 노출(단방향) |
| 전이 | ✗ | ✓ | - |
| CIDR 겹침 | 불가 | 불가 | **허용** |
| 규모 | 소수 | 수천 | 수천 소비자 |
| 비용 | 데이터만 | 어태치먼트+데이터 | 엔드포인트+데이터 |

#### VPN vs Direct Connect
| | Site-to-Site VPN | Direct Connect |
|---|---|---|
| 경로 | 인터넷(IPsec) | 전용선 |
| 구축 | 분~시간 | 수주~수개월 |
| 대역폭 | ~1.25Gbps/터널(ECMP ↑) | 1~100Gbps(+) |
| 지연 | 변동 | 일관 |
| 암호화 | 기본 | 없음(VPN/MACsec 추가) |
| 비용 | 저 | 고(전송 비용은 저) |
| 조합 | DX 백업/암호화 | 주 경로 |

#### Route 53 라우팅 정책 한눈에
| 요구 | 정책 |
|---|---|
| 비율 분배/카나리 | Weighted |
| 최저 지연 리전 | Latency |
| DR active-passive | Failover |
| 사용자 국가/대륙 기준 | Geolocation |
| 리소스 위치 + bias | Geoproximity |
| 여러 정상 IP 반환 | Multivalue |
| 클라이언트 CIDR | IP-based |

#### Security Group vs NACL vs WAF vs Network Firewall
| 요구 | 도구 |
|---|---|
| 인스턴스 간 허용 규칙(상태 저장) | Security Group |
| 서브넷 수준 IP 거부 | NACL |
| HTTP 공격(SQLi/XSS/봇/속도) | WAF |
| VPC 경계 도메인 필터/IPS, 중앙 검사 | Network Firewall |
| 서드파티 어플라이언스 삽입 | GWLB |
| DDoS | Shield |

### 단골 시나리오
- EC2 앱이 S3 접근 → **IAM 역할을 인스턴스에 연결**(액세스 키 금지).
- 다른 계정 리소스 접근 → **크로스 계정 IAM 역할 + STS AssumeRole**(서드파티면 외부 ID).
- 특정 리전/서비스 사용 금지를 전 계정에 → **Organizations SCP**.
- 온프레미스 AD 사용자로 여러 계정 SSO → **IAM Identity Center + AWS Managed Microsoft AD(양방향 신뢰)** 또는 AD Connector.
- DB 자격증명 자동 로테이션 → **Secrets Manager**(Parameter Store는 로테이션 없음).
- 키 사용을 감사하고 연 1회 자동 로테이션 → **KMS 고객 관리 키**.
- 규제상 HSM을 단독 통제 → **CloudHSM**.
- 공인 TLS 인증서 무료·자동 갱신 → **ACM**(ALB/CloudFront).
- 계정 침해·비정상 API·채굴 탐지 → **GuardDuty**. EC2/컨테이너 CVE → **Inspector**. S3 PII → **Macie**. 종합 점검 → **Security Hub**.
- "누가 버킷을 삭제했나" → **CloudTrail**. "버킷 설정이 규칙을 위반했나/변경 이력" → **AWS Config**(규칙 + 자동 수정).
- 메모리 사용률 모니터링 → **CloudWatch Agent**(기본 메트릭에 없음). 로그에서 특정 오류 카운트 알람 → **메트릭 필터**.
- AWS 계정 없는 PM에게 대시보드 → **CloudWatch 공유 대시보드(이메일/SSO 링크)**.
- 수백 EC2 패치 자동화/명령 실행/셸 접속 감사 → **Systems Manager(Patch Manager/Run Command/Session Manager)**.
- 서비스 한도 근접 경고, 유휴 리소스 → **Trusted Advisor**(Business 이상).
- 지난 2개월 EC2 비용을 인스턴스 타입별 비교·분석, 최소 노력 → **Cost Explorer**. 예산 초과 알림 → **Budgets**. 부서별 청구 → **Cost Allocation Tags**.
- 여러 계정/리전에 동일 인프라 배포 → **CloudFormation StackSets**.
- 개발자에게 승인된 템플릿만 배포 허용 → **Service Catalog**.
- 중앙 네트워크 계정의 서브넷/TGW를 다른 계정과 공유 → **RAM**.
