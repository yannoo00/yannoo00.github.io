### Data Storage & Analysis

<br />

**Snowball**

물리적인 장비를 배송해주고 거기에 대용량 파일 업로드해주면 S3 등에 업로드 해주는 것  
대역폭 안쓰고 네트워크 전송보다 빠름(수십 TB 등 초대용량의 경우)

<br />

**Glacier**

데이터 저장소인데 가끔 조회 되는 것 (저비용 장기 보관)

<br />

**S3 LifeCycle**

S3에서 일주일 후 Glacier로 이동 등 기간에 따라 적당한 곳으로 유배

<br />

**S3 VPC Gateway Endpoint**

프라이빗 서브넷에서 인터넷/NAT 없이 S3 접근, 무료

<br />

**Aurora, RDS**

일단 Aurora가 가용성, 확장성이 RDS보다 높아 기능적으로 RDS 상위 호환이지만 그만큼 운영 오버헤드가 있다.   
기존 사용하던 MySQL 등의 DB에서 가장 간단히 migration 하고 싶으면 RDS, 고가용성/재해복구 등 중요하면 Aurora....이기는 한데  
당연히 RDS도 Multi AZ 등의 설정을 통해 Failover에 더 튼튼하게 대비하는 등 여러 옵션은 있다. 

![](/img/posts/2026/11/mvys3gxq1wms.webp)

데이터 시각화 -> 어떤 대시보드를 누구한테 보여줄지는 IAM과 별개로 users & group으로 설정한다.   
(IAM role이 제어하는 것은 더 높은 수준의 분류.. 어떤 서비스 자체에 접근 가능한지?)

**AWS Glue ETL** 

메타 데이터 등을 다룸(데이터 변환)

<br />

**AWS Athena**

S3에서 바로 SQL(간편함에 초점)

<br />

**AWS Comprehend**

텍스트 분석 모델

<br />

**AWS Rekognition**

이미지 분석 모델

### Serverless

<br />

**Amazon SNS**

1:N의 구독자가 동시에 메시지를 받아서 소비해야하는 경우 특화(event 발생하면 바로 N개의 구독자에게 push)

<br />

**Amazon SQS(Simple Queue Service)**

메시지큐. SNS와 달리 메시지를 한 소비자만 처리  
SNS -> 어떤 서비스 ... 로 가는 과정에서 오류 방지나 부하 분산 등을 위해 버퍼링할 수 있음

- Visibility Timeout

  - 어떤 소비자가 가져가면 큐에서 보이지 않는 상태가 됨. 이 시간 이후 다시 큐에 보임. 한 개의 소비자가 처리 후 삭제해야하는 로직이면 처리 시간보다 visibility Time out 시간이 길어야 정상적으로 한 번만 처리될 수 있음

<br />

**Kinesis**

실시간 데이터 저장/처리에 활용 

- firehose

  - 받아서 s3등에 적재만
- data stream

  - 실시간으로 여러 소비자의 처리가 필요

<br />

**AppFlow** 

SaaS 서비스와 AWS 서비스 사이 데이터 전송을 단순화

### Network

<br />

**AWS Global Accelerator**

전 세계 어디서 접속하든 가장 가까운 AWS 엣지로 들어와 AWS 내부 고속망을 타고 가장 가까운 정상 리전의 애플리케이션(ALB/NLB/EC2)으로 연결해 주는 서비스  
cloudFront가 어플리케이션레벨(HTTP)이라면 이건 TCP/UDP 가속에 가까움 

<br />

**AWS Network Firewall** 

말 그대로 방화벽. VPC 내부의 트래픽 필터링 등에 쓰임

<br />

**ALB, NLB, GWLB** 

![](/img/posts/2026/11/mvyt4ld5kt7z.webp)

ALB -> HTTP(L7)  
NLB -> TCP/UDP(L4)  
GWLB -> IP(L3)
