트랜잭션 아웃박스는 트랜잭션의 일관성을 보장하기 위한 패턴으로,  
DB 트랜잭션 안에서 outbox 테이블에 이벤트를 쓰고, 릴레이가 브로커로 발행하는 방식을 칭한다.  

알림 기능을 구현할 일이 있었는데 이 때 구현상 알림은 다수의 유저를 대상으로 서버가 FCM(모바일 OS가 연결되어있는 서버)에게 요청을 보내야 했다.

기존에 작업하던 기능들은 클라이언트가 서버에 요청하면 서버가 응답해주는,  
\[클라 ----> API 서버 ---> DB ---> API 서버 ---> 클라]와 같은 단순한 구조였다. 이 API서버가 여러 개의 마이크로서비스로 쪼개져 있는 것이 아니기에 하나의 요청에 의해 다른 서비스에서 상태가 갈라지는 문제는 없었다.

하지만 알림을 대량으로 발송하는 방식은 다른 서버를 거쳐야만 한다.

![](/img/posts/2026/11/mwteyxtkos51.drawio.svg)

  
위와 같은 구조로 발송된다.  
하나의 작업이 DB와 FCM, 트랜잭션을 공유하지 않는 두 시스템에 써야 하는 것이다.

DB/FCM의 정합성을 맞추기 위한 방법을 고려해보자.

- FCM이 먼저 보내고 DB 커밋

  - DB 커밋에 실패하면 사용자는 알림 푸시를 받았는데 DB에는 안 받은걸로 기록됨
- DB 먼저 커밋하고 FCM 발송

  - 커밋은 됐는데 FCM에서 오류내서 안보내지면 DB에는 쓰였는데 사용자는 알림 못받음

이 두 방식에서는 모두 정합성이 깨진다.

<br />

이번에는 알림 아웃박스를 만들어보자.  
알림 아웃박스는 보내야하는 알림 목록과 상태를 들고 있는다. 최초에 알림을 보내야하는 유저 목록이 이 테이블이 된다. 상태는 pending이다.   
그 후 발송기가 행을 가져가면서 sending으로 바꾸고 FCM을 호출한다. 결과에 따라 sent(성공), pending(일시 오류, 나중에 재시도), failed(최종 실패)로 바꾼다. fail이 DB에 그대로 남아있기 때문에 오류에 대한 재전송도 가능하고, 아웃박스가 source of truth가 된다. 

정리하면 다음과 같다.

\[트랜잭션 1]  INSERT 알림과 함께 처리되어야 하는 작업 + INSERT notifications(push_status = 'pending') -> COMMIT

[트랜잭션 2] pending -> sending으로 바꿔서 COMMIT 

\=> 여기서 FCM 호출

\[트랜잭션 3] 결과에 따라 sent / fail / pending으로 바꾸고 COMMIT

<br />

이렇게 아웃박스는 해야 하는 일(메시지를 발송해야한다는 사실)을 먼저 DB에 적는다.  
적은 후에 이 기록을 보고서만 반드시 외부로 호출한다. 끝날 때까지 - 릴레이.  
(내 경우에서는 이게 FCM으로 기기에 알림 보내는 것)
